# ADR-032：实时协作通道与在场模型

> 状态：ACCEPTED（设计，待 M11-I01/A01 实现）<br>
> 日期：2026-10-09<br>
> 归属：M11-S01 合同冻结；验证原型见 [M11-S01 冻结记录](../spikes/M11-S01-实时协作与WorkGraph合同冻结.md)<br>
> 关联决策：[ADR-021](ADR-021-三流恢复与前端合并协议.md)（三流恢复协议，本 ADR 不修改其任何边界）、[ADR-038](ADR-038-团队成员生命周期与责任转移.md)（成员撤权，M11 增补新通道部分）、[ADR-007](ADR-007-API命令与并发协议.md)<br>
> 影响里程碑：M11

## 背景

M11 需要双向实时协作信号：在场（谁正在查看该资源）、正在输入、实时变更通知。当前事实：全部实时面是 Spring WebFlux SSE（7 个端点、纯数据库有界轮询），零推送基础设施；WebSocket 代码与依赖均为零，引入是新依赖决策。M11 Release Gate 第 1 条规定「WebSocket 不参与权威状态恢复」，这是本 ADR 全部分工的立法前提。

## 决策

### 通道分工与降级

| 信号 | 通道 | WebSocket 完全不可用时的降级语义 |
|---|---|---|
| 在场（谁在看） | 仅 WebSocket | 功能显式不可用，界面呈现降级态；**不开设在场 SSE 替代通道** |
| 正在输入 | 仅 WebSocket | 同上 |
| 实时变更通知（稳定坐标 + 新版本，零业务负载） | WebSocket 推送（增强） | 权威更新不受影响：既有 Team Activity SSE 流与 REST 回读本就完整覆盖，仅损失推送时延；界面退化为既有轮询节奏 |
| Team Activity 耐久事件流 | SSE（不动） | — |
| Conversation 事件流 / AG-UI invoke+resume / Task 事件流 | SSE（不动） | — |
| 恢复 / 回放 / 游标 | 仅 SSE（ADR-021 签名游标） | WebSocket 不承载任何可回放状态；重连后经 REST + SSE 重建 |

依据：在场与输入是易失信号，丢失不影响业务正确性（Release Gate 第 2 条）；耐久流已有成熟恢复协议，不需要第二条恢复路径。前端在既有 `activityRealtimeStore`（SSE 面，九相状态机）之外新建独立的 collaboration 实时 store（五相：idle / connecting / live / degraded / reconnecting），复用同一指数退避常量 `min(8000, 500 × 2^min(attempt,4))`；两个 store 互不接管对方的流。

### 握手与鉴权：复用 Session，不建第二套 token

- WebSocket upgrade 是普通 HTTP 请求，先过既有 reactive filter 链：`SameOriginWebFilter` 校验 Origin 一致性（这是防 cross-site WebSocket 劫持的控制；CSRF 不适用于 GET 握手），security chain 对 `/ws/**` 设 `authenticated()`，未认证握手返回 401 不开启升级。
- 会话身份由既有 `WebSessionServerSecurityContextRepository` 从 `CREWSCOPE_SESSION` cookie 解出，WebFlux 没有 MVC 的 HandshakeInterceptor，等价物是握手请求过 security chain 后、WebSocket handler 内通过 `WebSocketSession.getAttributes()` 读取注入的 principal。**Spring Framework 7 行为（S01b 实测修正）**：该 map 默认为空，只有给 `HandshakeWebSocketService` 配置 `sessionAttributePredicate` 才会从 WebSession attributes 按键名白名单拷贝——产品必须显式配置该 predicate（允许 principal 相关键，拒绝其余），不能沿用 6.x 的 exchange attributes 直觉。
- 重连协议：客户端退避重连 → 浏览器自动重带 cookie → 服务端完整重新握手鉴权 → 客户端重发 subscribe → 服务端逐条重新授权。**不回放 WebSocket 历史，权威状态一律走 SSE/REST**。
- WebSocket 层对成员事实只读；全部成员写操作仍走 `TeamMemberLifecycleApplicationService` 唯一入口，不新增第二处成员命令入口。

### 心跳与连接生命周期

- 服务端每连接 15s 发 ping（对齐 Team Activity heartbeat 常量）；30s 无入站帧即断开（对应既有 SSE `maximumEventsPerConnection` 的有界轮换思想：连接是可丢弃、可重建的资源）。
- 出站走有界缓冲：缓冲满或发送超时的慢客户端被断开，不无限堆积（慢客户端处置交由 I01 实现并验收）。

### 在场数据模型：只存 Redis + TTL

- 连接键（TTL 载体）：`crewscope:{env}:collaboration:v1:presence:conn:{connectionId}`，hash 字段 `{organizationId, teamId, principalId, resourceType, resourceId, connectedAt, lastSeen}`，**TTL 45s（= 3 × 心跳 15s，容忍丢两次心跳）**。
- 索引键（fanout 载体）：`crewscope:{env}:collaboration:v1:presence:scope:{org}:{team}:{resourceType}:{resourceId}`，ZSET，member = connectionId、score = expireAtEpochMs；读写路径先 `ZREMRANGEBYSCORE -inf now` 惰性清理，另由 I01b 交付定期清扫（惰性清理只发生在被访问的 scope）。
- 多标签：同一浏览器多标签共享一个服务端 Session，但**每标签页一条独立 WebSocket 连接 = 一个 conn 键**；呈现层按 principalId 去重为一个头像。连接预算按原始连接数计（200 含多标签展开）。
- 红线：在场/输入信号只存 Redis 带 TTL，**不进 PostgreSQL、不进 Outbox、不进 Audit**；Redis 清空不影响业务正确性，只损失瞬时呈现。

### 撤权（三层协议；完整合同见 ADR-038 M11 增补）

1. 事件层（快路径）：既有 Outbox → `IdempotentEventDispatcher` 增加消费者（M11-D02 交付），消费成员生命周期事件 → 查连接注册表 → close（应用码 4403）+ 删 Redis 键。
2. 复验层（正确性兜底）：每个出站帧（含心跳）复验成员有效性与 authorizationVersion，带 ≤5s 缓存（对齐既有 SSE idle-probe 5s 先例）；每次 subscribe 重新求交授权。
3. TTL 层（上界）：前两层全失效时，在场 45s 内自然消失，连接 30s 无入站即断。

单实例部署下注册表与消费者同进程直连；多实例演进需要跨进程控制通道（Redis pub/sub）时按重新评估条件增补。

### 容量与背压上限（阈值；实测数字由 M11-S01b 回填冻结记录 §4）

- 每 principal 并发 WebSocket 连接 ≤ 16；每 Team 并发连接 ≤ 300；单节点软预算 200、硬上限 500（软预算超出进入告警，硬上限拒绝新握手）。
- 每连接订阅数 ≤ 32；订阅粒度为 Team / WorkProject / 资源三级。
- 消息预算（50 人同屏，公式冻结）：入站 ≈ 50 × (1/15 心跳 + typing 5s 窗口 2 帧 + 2/min 状态迁移) ≈ 22 msg/s 峰值；出站 fanout = 每条在场迁移 × 同 scope 订阅者数；Redis 写 ≈ 3.3 writes/s 稳态。typing 合并：5s 有效窗口内只发 started / stopped 两次，不逐击键转发。

### 变更通知合同

- 通知载荷只含稳定坐标（资源类型 + ID + Scope）与新版本号，**不含业务负载、不含资源标题**（在场可见性红线：未授权者连资源存在性都不可推断，M11-Q01 攻击集第 3 项）。
- 收到通知的前端动作是提示横幅（「该工作项已被更新，点击刷新」）或带版本条件的受控回读，不是自动覆盖用户正在编辑的内容；冲突判定仍走既有强 ETag（If-Match）乐观锁，不引入 CRDT。

## 实现约束

- 落点：协作信号落既有 `application/collaboration/` 与 `domain/collaboration/`（不新建 `application/presence`）；server 侧 `CollaborationSignalController`；DTO 平铺 `server/api/`。
- 依赖引入方式：`org.springframework:spring-websocket`（版本由已前置 import 的 spring-framework-bom 管理），**不用 `spring-boot-starter-websocket`**（它会传递 spring-boot-starter-web 即 Tomcat/MVC，与 WebFlux/Reactor Netty 栈冲突）。
- 部署面：team-beta Nginx 需补 `map $http_upgrade $connection_upgrade` 与 `proxy_set_header Upgrade/Connection`（I01c 交付）；SSE 既有配置不动。
- 撤权协议与成员命令边界以 ADR-038 增补小节为准。

## 结果

- 三条耐久流与 AG-UI 的恢复协议零改动；WebSocket 只承载可丢弃的双向信号。
- 在场数据可全量丢失重建；撤权最坏失效窗口 = 5s 复验缓存 + 一个心跳间隔，与 SSE 已接受窗口同量级。
- 单节点 200 连接预算有明确阈值与度量口径（S01b 原型实测）。

## 验证

1. M11-S01b 隔离原型（ws-probe + 压测七场景）验证机制保真度：握手鉴权复用、在场 TTL、撤权断连、多标签去重、fanout 与慢客户端处置——见冻结记录 §6。
2. 产品级验收归 M11-I01（200 并发连接延迟与内存基线、连接风暴、订阅泄漏、SSE 降级端到端）与 M11-Q01（跨 Team 订阅、撤权残留攻击集）。

## 重新评估条件

- 多实例部署需要跨进程连接控制通道（Redis pub/sub 或等价物）时增补本 ADR 的事件层协议；
- 产品需要 WebSocket 承载可回放状态（与 ADR-021 恢复边界合并）时重新评估通道分工；
- 50 人同屏实测消息量显著超出 §容量公式冻结值时重新核定预算。
