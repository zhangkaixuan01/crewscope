# ADR-026：M8 产品化与工程收口合同

> 状态：PROPOSED<br>
> 日期：2026-09-01<br>
> 影响里程碑：M8<br>
> 关联文档：[M8 执行清单](../plans/M8-产品化与工程收口.md)、[CrewScope 实施计划](../CrewScope-实施计划.md)

## 背景

M0–M7 已经形成 Team Beta 的核心执行闭环，但产品从“能够运行”进入“可以持续交付”还需要统一的配置入口、稳定的发布坐标、可验证的运行边界和可持续的质量反馈。M8 同时涉及 Web、应用服务、基础设施、AgentScope Runtime、Worker、CI 和部署；如果先写代码再补合同，容易出现 Readiness 与领域事实漂移、Setup Center 暴露内部错误、GitHub 导入绕过受管仓库边界、发行镜像与源码版本不一致以及 Worker 继续持有宿主机控制面等问题。

本 ADR 冻结 M8 的公开行为、安全边界、质量门禁和验收证据。后续工作包可以在该合同内实现，但不得以实现便利改变这些边界。

## 决策

### 1. Team Setup Readiness 合同

Readiness 是查询时从权威事实派生的只读视图，不新增可写状态表，也不复制 Model、Agent、Provider、WorkProject、Repository 或 Runtime 的生命周期。查询必须在当前 Organization、Team、Member 和权限范围内完成，并带有单调的 `snapshotVersion` 或等价版本坐标。

每个能力项使用闭合状态：

```text
READY | ACTION_REQUIRED | BLOCKED | UNAVAILABLE
```

公开项至少包含 `capability`、`required`、`status`、稳定 `reasonCode`、`canConfigure`、责任主体摘要和可选的受信站内 `actionKey`。公开响应禁止包含 Credential、API Key、Secret、Endpoint、Remote URL、宿主机路径、Provider 原始错误、数据库坐标和任意外部跳转地址。

能力级就绪固定为：

| 能力 | 必需事实 | 可选事实 |
|---|---|---|
| Personal Conversation | 当前账号、Team Membership、可用 Personal Agent/模型 | GitHub、飞书 |
| 普通团队任务 | Team、成员责任、可用执行 Runtime | 外部 Provider |
| Coding/Review | WorkProject、受管 Repository/CodingTarget、Coding/Reviewer Agent、Sandbox 健康 | GitHub Draft PR |
| GitHub Draft PR | 已验证 TEAM Connection、Allowlist、导入完成的 Managed Repository、Push Lease | 飞书通知 |
| 飞书通知与 Team Observer | 已验证 TEAM Lark Connection、通知策略和只读查询权限 | GitHub |

可选集成缺失不能阻断基础对话和站内 WorkItem。状态计算必须满足最小权限：无配置权限的成员只能看到缺失项、责任人和文档化的下一步，不能获得写入动作。

### 2. 受信站内动作边界

`actionKey` 不是 URL，也不是前端可自由拼接的命令。服务端只发布固定枚举值，例如 `OPEN_MODEL_SETTINGS`、`OPEN_AGENT_SETTINGS`、`OPEN_WORKPROJECT_SETTINGS`、`START_GITHUB_IMPORT` 和 `OPEN_LARK_SETTINGS`。前端将其映射到同源、预注册的路由或既有业务 API；服务端在执行动作时再次进行 Team、Member、Role 和资源授权校验。

浏览器不得提交 Remote URL、Token、任意 Provider Endpoint 或宿主路径。GitHub 导入只接受已验证 Connection、External Repository ID、WorkProject、稳定 Repository Key 和 Branch；导入成功后必须复用现有 `LOCAL_MANAGED` RepositoryBinding 创建流程。

### 3. GitHub 导入与 Worker 隔离

导入任务以有界 `ImportJob` 表达，支持幂等、进度、取消、重试、恢复和审计。Worker 通过短期凭证将 bare mirror 写入 Managed Root，并校验 owner、路径、bare 格式和基线 Ref。任何越界、撤权、凭证失效或远程漂移均以稳定失败码结束，不把远程响应原文传给浏览器。

Coding/Review 执行环境不得默认获得宿主 Docker Socket 或等价的无限控制权限。M8-I03 必须落地独立 Docker Daemon、受限 Socket Proxy 或经安全评审批准的等价边界，并用逃逸、Worker 被攻破和 API 不可用场景证明控制面不可达。隔离等级、残余风险和运维操作必须写入部署文档。

### 4. 错误、日志和隐私

公开 API 只返回稳定错误码、可重试提示和相关请求标识。Provider 原始错误只保留在服务端受控日志/Trace，且经过字段白名单和脱敏；Secret、Credential、Session、Token、密码、Remote URL、Endpoint、内部路径和数据库坐标不得进入日志、事件、Audit、Trace、指标、快照或前端持久化。

### 5. 三层质量与发布门禁

- **PR Gate**：按变更范围执行格式、编译、单元/契约测试、前端测试、敏感字段和文档链接检查；路径过滤只能缩小无关工作，不能跳过受影响模块。
- **Main Gate**：执行完整 Java、Web、集成、浏览器、迁移、恢复和安全回归，并保存 Revision、环境和 Artifact 索引。
- **Release Gate**：只接受受保护 Tag 和干净源码；验证 Backend/Web 同一 Git Revision 的 GHCR 镜像、固定 Digest Manifest、SBOM、Provenance、签名、安装、升级、备份恢复和真实浏览器闭环。缺失或篡改任何证据均失败关闭。

首个正式发行坐标为 `v0.1.0-beta.1`，支持 Linux amd64、单机 Team Beta、PostgreSQL、Redis 和 GHCR。镜像标签可读，部署必须使用 Digest；Release Notes、升级说明、安全报告和贡献指南与 Tag 同步发布。

### 6. 兼容性与重构

M8-E01 的大文件拆分必须先建立 Characterization/Contract Test，再移动编排、查询、映射、SQL、DTO、状态和控制职责。公开 API、数据库事实、事件 Schema、幂等键、权限策略、Worker 恢复和前端行为前后保持一致；仅凭文件行数或类数量不能判定完成。

## 验收证据

每个 M8 工作包必须记录：Git Revision、命令与版本、环境 Profile、测试结果、失败样本、日志/Trace 脱敏检查和可复现 Artifact 链接。M8-Q02 额外固定以下五类 Fixture：

1. 新 Team：只有账号、Team 和默认 Personal Agent；
2. 已配置 Team：模型、Agent、WorkProject 和 Runtime 均可用；
3. 无权限成员：可读但不能配置；
4. Provider 故障：连接不可达、撤权或原始错误包含敏感字段；
5. 部分配置：基础对话 READY，Coding、GitHub 或飞书分别 ACTION_REQUIRED/BLOCKED。

M8 Release Gate 必须证明：新 Team 无需手工改库即可从 Setup Center 进入 Personal Conversation；GitHub 导入结果进入 Managed Catalog 并可创建 CodingTarget；Worker 控制面隔离；Trace 可查询或被明确关闭；告警可达；备份可恢复；发行镜像可验证；M0–M7 固定门禁零回归。

## 接受与重新评估

本 ADR 在 M8-S01 产出后作为 PROPOSED，M8-A01、M8-A02、M8-I03 和 M8-Q02 的证据通过后转为 ACCEPTED。发生以下变化时必须新增 ADR 或修订本 ADR：支持新的部署拓扑或架构、引入企业身份/密钥服务、扩大 Provider 或 URL 暴露范围、改变事件/API/数据库兼容语义、取消签名或 Digest 发布、或 Sandbox 隔离等级发生变化。
