## 背景与源码基线

当前 TeamMember 已有 activate/suspend/leave/remove、乐观版本与 canParticipate，不能另建第二套成员实体。普通 HTTP 经 TeamRequestIdentityResolver 与领域服务校验；TaskTokenCurrentAuthorization 检查 execution/current attempt/fencing、责任版本、用户或 Agent owner 的成员有效性；TeamActivityController 建立连接及逐帧检查，ConversationEventController 每次轮询重新解析身份并调用受权事件查询。

这些保护不是“所有在途执行已可撤权”的证明：PersonalAgentInvocationService 使用 ReplayableExecutionSegment 保留流/回放；CurrentActionAuthorityFactsResolver 重读 Owner 责任、Review、Binding、Connection/Grant，却没有 TeamMember repository；GitHubActionAuthorityValidator 检查 Binding/仓库版本，不能替代当前操作者成员授权。授权撤回与外部网络写入间也不可能有跨系统数据库事务。

因此选择复用现有领域、逐边界补当前事实校验、撤权提交与交接分离，不引入新的权限平台、Saga 平台或独立 Worker 服务。

## 1. 命令、最小权限与锁序

- 角色变更需当前有效成员的 ROLE_MANAGE；停用/移除/恢复/邀请需 MEMBER_MANAGE。授予或撤掉 TEAM_OWNER、停用/移除 Owner 另需操作者当前是 TEAM_OWNER；不能把能邀请 MEMBER 等同能创造 Owner。自助离开仍应用最后 Owner 保护，不授予管理他人的能力。
- 恢复/重新加入要求新一次明确命令和强版本；恢复默认 MEMBER，显式授予其他角色另校验 ROLE_MANAGE/Owner 权限，不自动恢复旧高权角色、旧确认、旧 token 或在途运行。旧授权记录保留审计，不删除历史。
- 命令事务固定为：验证当前身份 → 锁 Team 行 → 在锁内重读操作者、目标成员、有效角色/版本 → 验证最后 Owner → 更新成员/角色授权版本 → DomainEvent/Outbox/回执结果 → 提交。既有邀请/成员修改等参与相同不变量的写入口都要遵守 Team 锁，不能只锁新接口。
- 同 Team 成员/角色多对象锁按 ID 排序；交接 item 再按 WorkItem → assignment/Task 顺序锁。禁止一个路径先锁成员再等 Team、另一个反序。幂等回执的预留不能让重放跳过当前读取权限。
- 最后 Owner 定义为**当前 ACTIVE/canParticipate 成员 + 当前有效、可授予的 TEAM_OWNER grant**，不是表中角色字符串数量。移除/停用/降级任一入口都保证提交后至少一个有效 Owner。两个 Owner 同时退出只能一个成功，另一个 409，不能靠先读 count 再分别更新。
- 要替换最后 Owner，使用一次明确的 Owner 转移事务，在相同 Team 锁下校验接收者当前有效并先建立新 Owner，再撤旧 Owner；不能把“责任交接后台任务”当作 Team Owner 的替代保障。

## 2. 撤权事实与提交时点

新增成员 `authorization_version`（初始 1），成员状态或有效角色变更递增。它与普通资料/activity version 分开，避免更新 lastActiveAt 导致运行上下文失效。MemberRole 写侧也必须在 Team 锁内递增对应成员 authorization_version。

成员命令提交的时点 T 为撤权生效点。其后发起的新请求、续读/续流、模型/工具/外部写调用必须重读成员当前事实；不能等交接完成、浏览器刷新、token 自然过期才拒绝。Outbox/事件用于快速清理，不作为授权唯一来源；缓存校验失败或数据库不可用时失败关闭，不使用旧缓存放行。

执行授权快照增加发起成员、实际执行成员/Agent owner 的 id+authorizationVersion（按适用范围），并保留已有 assignment version、scope、policy hash、fencing。旧快照缺新维度时，允许受权读取历史，但下一个副作用边界须重新授权/形成新快照；不能把缺字段默认填当前版本而声称旧确认仍有效。API-only 启动不要求存在运行快照。

Team 停用一个成员不得全局禁用其 Organization Principal/账号，也不得误伤另一 Team 的会话与个人连接。个人 Agent 的运行须检查其 owner 在当前 Team 的状态；团队 Agent 的生命周期本身不因某普通发起者离开而删除，但该发起者授权启动的运行必须重新取得合法授权。

## 3. 通道与执行检查点

| 路径 | 现有入口 | A07 必须接入的持续检查 |
| --- | --- | --- |
| HTTP/读模型 | TeamRequestIdentityResolver、领域 AccessPolicy、BrowserPermissionProjection | 每请求读当前成员/角色；敏感命令提交前锁内复验；前端菜单可用性不能代替后端 |
| Team SSE | TeamActivityController 的 requireTeamAccess/authorizeFrame | 逐事件披露前核验当前版本；无事件时最长 5 秒检查并关闭失效订阅；不能只等下一条业务事件 |
| Conversation 投影/SSE | ConversationEventController 的 resolve/page；ConversationApplicationService.requireReadable | 每批查询及每帧披露前核验成员和 PRIVATE/参与范围；批次读取后到发送前撤权不得继续吐出剩余正文 |
| Personal Agent/AG-UI | PersonalAgentInvocationService.invoke/resume/publisher、ReplayableExecutionSegment | 每次模型/工具调用、消息/TaskIntent 提交、瞬态事件及缓存回放前核验当前 owner/成员/授权版本；注销订阅不冒充取消 Agent |
| Task/Coding Worker | TaskTokenCurrentAuthorization、DurableTaskWorkerExecutionHandler、BuildProfileCommandRunner 的 guardedCall.requireCurrent | claim、lease renewal、模型/工具/命令调用前和业务结果提交前核验；失效 fencing 不能继续落状态；尽力停止沙箱，不对已执行命令宣称回滚 |
| GitHub Action Worker | CurrentActionAuthorityFactsResolver、ActionWorker、GitHubActionAuthorityValidator | resolver 补当前 Owner/发起成员有效性；Claim 和外部适配器调用前重验精确 authority；撤权后的 READY 不因恢复成员自动变可执行 |
| Notification Worker | DefaultNotificationRecipientAuthorization、当前映射/偏好/Grant 快照 | 保留源版本/收件人当前授权；失效不投递，不能以个人偏好自助接口越过团队通知策略 |
| 后续 WebSocket/在场 | M11-D02，当前无此新增实现 | 订阅/消息/回放按同一 authorizationVersion 接入，不复制生命周期命令/表 |

5 秒是无业务事件时订阅失效探测上界目标，不是允许 5 秒继续披露的窗口；每次发送仍先检查。不能承诺离线浏览器已显示内容即时消失。F05 在事件/401/403/重连时先隐藏再清受影响 Scope，恢复身份之后才展示旧本地内容。

## 4. 外部提交、UNKNOWN 与恢复

授权检查与数据库内变更可通过同一事务/Team 锁串行；网络请求不可把数据库锁一直持有到远端完成。选择如下可实现语义：

1. T 后的新调用，调用前校验拒绝；已经校验但尚未交给适配器时收到撤权，取消发送。
2. 请求已交给操作系统/远端或无法确定是否交付时，撤权只阻止后续新动作；不承诺撤回已发 Push、PR、通知或模型请求。记录安全 dispatch/时间/authority 证据，已知结果据实登记，未知进入既有 UNKNOWN/RECONCILING。
3. 对账继续使用只读 query-only 协议；远端仍需有效凭据/受权系统身份。无安全查询权限则保留 UNKNOWN、显示需要有权者处理，不能为了查结果重放写请求或扩大 Grant。
4. 成员恢复、换 Owner、交接完成不会复活旧 Confirmation。当前有权 Owner 读取原外部事实，必要时新计划/新精确确认；原已成功动作不再发送。
5. 晚到响应可登记不可变外部结果/审计事实，不可使失效运行再次取得执行权；不能向已撤权浏览器披露其内容。内部审计/结果落库与继续业务执行分别鉴权。

精确保证是“撤权后的新授权边界拒绝”，不是物理网络上的瞬时撤回。并发测试必须区分撤权前已交付、校验后尚未交付、响应丢失三种情况。

## 5. 责任交接：耐久、按项、无隐式高权

停用/移除提交即拒绝新授权。既有责任可保留历史关联但成为不可用责任，页面明确“需要交接”；不把移除者的所有工作静默分配给操作者。最后 Team Owner 必须先依 §1 处理，不能用此状态绕过。

交接新增具体领域 job/item（不是通用流程引擎）：

```text
job: org/team/sourceMember/targetPrincipal/role/commandId/createdBy,
     sourceAuthorizationVersion/status/createdAt/updatedAt
item: jobId/assignmentId/workItemId/expectedAssignmentVersion,
      state(PENDING|DONE|CONFLICT|DENIED)/resultAssignmentId/errorCode
unique(jobId, assignmentId)
```

- 创建交接需 MEMBER_MANAGE；每项责任修改还需 RESPONSIBILITY_MANAGE 和项目/候选合法性；针对 Owner/Gate Reviewer 保留人类主体、分离职责等现有规则。目标是当前有效受权人/Agent，不因批量交接绕过角色限制。
- 用户确认前展示范围/角色/数量；一次最多 100 个具体责任项，不提供未经确认的无界“全部项目”后台变更。选择固定 id/version，不按 job 执行时的列表重新选目标。
- 每项在事务内 CAS 原 assignment/version → 新责任 → 对应事件/结果 → item checkpoint；源责任已变更或目标已失效时记 CONFLICT/DENIED，不覆盖新事实。每项提交后才推进进度，job 是聚合计数。
- 中断/进程重启按 jobId 继续，DONE 不重发。重复原命令返回原 job；更换目标或处理冲突用新确认/新命令，仅选择未完成项。允许取消尚未处理项，但已成功项不自动回滚。
- 交接失败不恢复已撤回权限；恢复成员是另一个显式命令。固定 job 结果接 S01/D01 恢复接口，管理页按 job 定点查询，不能找“最新交接”。

## 6. 升级与验证

追加 Flyway：member.authorization_version、具体 job/item 及索引；旧成员赋初始版本、既有责任/历史事件不改写。旧授权快照处理按 §2；不扫描日志“重建”权限。新后端先上线，新前端消费明确能力；旧客户端继续使用既有读/邀请，不提供弱化的生命周期降级路径。

本 S01 的隔离 PostgreSQL 原型已验证 Team 行锁下两 Owner 并发停用只成功一个、他 Team 不变、交接 checkpoint 跨 SQL 会话重试不重复增加 assignment 版本。现有 TaskTokenCurrentAuthorization 等回归另列 S01 证据。**原型不是完整 A07 实现测试**。

A07 必须交付真实仓储/应用/API 集成：所有 Owner 变更入口并发、状态/角色版本 CAS、发起者与执行者撤权、无事件 SSE/缓存回放、撤权与远端提交三种竞态、交接部分成功/重启/冲突、恢复不复活旧授权、另一 Team 不受影响。Q01/Q02 补真实后端浏览器与授权外部验证；无需真人验收。

重新评估条件：增加跨 Team 责任、跨数据库事务、多实例订阅总线或新实时通道时增补本 ADR；不得以部署简单为由删除持续授权。仍使用四服务 HTTP、API 内 Worker，不新增独立授权/交接服务。
