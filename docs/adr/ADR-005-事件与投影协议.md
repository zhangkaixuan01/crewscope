# ADR-005：DomainEvent、Outbox、Audit 与实时事件

> 状态：ACCEPTED<br>
> 日期：2026-08-05<br>
> 更新：2026-08-11（M2-A05 固化 TaskIntent Candidate 与 Conversation Event 协议）<br>
> 影响里程碑：M0–M6

## 背景

CrewScope 同时提供 AG-UI AgentRun 流、Conversation Event 流和 Team Event 流。业务事实、实时交互和投影更新需要稳定关联，前端需要处理断线、重复、乱序和 optimistic state。

## 决策

### 事实与投影

- PostgreSQL 领域聚合是业务事实源；
- 领域状态、DomainEvent 和 Outbox 在同一事务提交；
- Outbox Publisher 使用至少一次投递；
- ProjectionCheckpoint 保存投影分区和最后处理位置；
- AuditEvent 是追加写安全投影；
- Activity、Inbox、Notification 和 WorkGraph 是可重建读模型。

### DomainEvent 信封

DomainEvent Payload 只表达业务事实。身份、类型、版本、租户、聚合、操作者和关联链由 Envelope 统一承载：

```text
eventId
eventType
schemaVersion
organizationId
teamId
workspaceId
aggregateType
aggregateId
aggregateVersion
actorType
actorId
correlationId
causationId
idempotencyKey
occurredAt
payload
```

`teamId`、`workspaceId`、`actorId`、`causationId` 和 `idempotencyKey` 是可选字段。`eventId`、`correlationId` 和已提供的关联 ID 使用非 Nil UUID。`aggregateVersion` 从 `0` 开始，表示产生该事实的已提交聚合版本。

### 统一实时事件信封

AG-UI、Conversation Event 和 Team Event 共享：

```text
eventId
domainEventId
streamType
eventType
schemaVersion
aggregateType
aggregateId
aggregateVersion
correlationId
causationId
occurredAt
payload
```

一个 DomainEvent 进入多个流时保持相同 `domainEventId`、`aggregateVersion` 和 `correlationId`。每个流生成独立 `eventId` 和 Cursor。AG-UI 瞬时进度事件的 `domainEventId`、`aggregateType`、`aggregateId` 和 `aggregateVersion` 为空。

### JSON 与版本兼容

- 外部 JSON 字段使用 camelCase，字段写出顺序固定；
- 所有可选字段写出为具体值或 JSON `null`；
- 读取时同时接受缺失和 `null` 的可选字段；
- 读取时忽略新增的未知 Envelope 字段；
- Envelope 根节点和 Payload 必须是 JSON Object；
- `eventType` 与 `aggregateType` 使用大写下划线命名；
- `schemaVersion` 使用从 `1` 开始的十进制字符串，每种 `eventType` 独立演进；
- 时间使用 UTC RFC 3339 文本，并与 PostgreSQL `TIMESTAMPTZ` 统一到微秒精度；
- 字段删除、改名、改变含义和改变类型需要发布新的 SchemaVersion；新增可选字段保持当前 SchemaVersion；
- 领域层不依赖 JSON 库，application 层使用 Spring Boot 4 管理的 Jackson 3 手工构造 Envelope JSON Tree。

V1/V2 数据库中的 `subject_type` 和 `subject_id` 对应 `aggregateType` 和 `aggregateId`。V3 新增 `aggregate_version` 列并完成 DomainEvent、Outbox 与 Envelope 的事务映射。

### 事务写入协议

状态变更应用服务通过 REQUIRED `TransactionExecutor` 执行以下顺序：

```text
提交聚合快照
  -> 追加 DomainEvent
  -> 创建 PENDING Outbox
  -> 提交数据库事务
```

DomainEvent Store 和 Outbox Repository 使用 MANDATORY 传播级别，只接受已有事务。任一步失败时聚合快照、DomainEvent 和 Outbox 一起回滚。模型、Provider、Connector、Webhook 和消息发布在事务提交后执行。

M0 使用统一 Topic `crewscope.domain-events.v1`。Outbox 分区键格式为 `{organizationId}:{aggregateType}:{aggregateId}`，同一 Organization 内同一 Aggregate 的事件进入相同发布分区。Outbox Payload 通过 `domain_event_id` 关联 DomainEvent 读取，事件事实只保存一份。

### Outbox 发布协议

Outbox 使用独立的轮询 Publisher，每轮执行三类短事务：

```text
回收达到上限的过期租约
  -> FOR UPDATE SKIP LOCKED 批量 Claim
  -> 事务外并发发布
  -> 逐条确认 DELIVERED 或记录失败
```

Outbox 状态为 `PENDING`、`CLAIMED`、`DELIVERED` 和 `DEAD_LETTER`。Claim 写入 `claim_token`、`claimed_by` 和 `claim_expires_at`。成功、失败和回收仅在状态、Claim Token 和租约仍匹配时生效，过期 Worker 不能确认新租约。

`retry_count` 表示已失败的发布尝试数。发布异常时立即加一；Claim 后崩溃在租约过期回收时加一。未达上限的事件回到 `PENDING`，使用有上限的指数退避设置 `next_delivery_at`；达到上限后进入 `DEAD_LETTER`。

每个 Topic 和分区键只能按 `aggregateVersion`、`occurredAt`、`eventId` 领取最早的未终结事件。正在投递或退避的前序事件阻止后续事件；`DELIVERED` 和 `DEAD_LETTER` 不阻止分区继续。不同分区可并发发布。

Publisher 提供至少一次投递。外部发布成功后进程崩溃会产生重复事件。消费者使用稳定 `consumerName + eventId` 作为幂等键，在同一本地数据库事务中写入消费回执并执行副作用。失败事务不保留回执，重试可重新处理。

### Projection Runner

每个投影使用稳定 `projectionName`，并以 `organizationId + projectionName + partitionKey` 定位 ProjectionCheckpoint。本地投影事务执行：

```text
插入 consumerName + eventId 回执
  -> 创建或锁定 ProjectionCheckpoint
  -> 校验 aggregateVersion
  -> 写入投影副作用
  -> 推进 Checkpoint
  -> 提交本地事务
```

新分区的首个事件版本必须为 `0`。已有分区接受相同 `aggregateVersion` 中按 `occurredAt + eventId` 排在 Checkpoint 之后的事件，也接受 `lastAggregateVersion + 1`。低于已处理位置的事件作为过期重放忽略，高于期望版本表示缺口。缺口不推进 Checkpoint，也不保留消费回执和部分投影。

Checkpoint 的 `last_event_cursor` 在 M0 使用 `aggregate-version:{n}`，同时保存 Event ID 和发生时间。运行时不保留内存游标，新进程通过数据库 Checkpoint 继续。

M0 Audit Projector 将每个 DomainEvent 生成一条追加写 AuditEvent。AuditEvent 保留 Organization、Team、Workspace、Actor、Subject、Correlation、Causation、SchemaVersion、OccurredAt 和业务 Payload。领域 Actor 为用户时同时记录 Initiator，为 Agent 时记录 Agent Principal；缺失的上下文保持为空。

### Command Receipt

所有状态变更 Command 返回：

```text
commandId
domainEventId
committedVersion
correlationId
```

前端提交后展示 optimistic state。目标投影 Cursor 到达对应 domainEventId/committedVersion 后清理 optimistic state。超时后回读当前事实。AG-UI 的瞬时事件用于公开回答与受控运行进度，不覆盖领域状态。

### 受控 AG-UI 入口

CrewScope 不开放 AgentScope Starter 自动注册的通用 `/agui/run` 和 `/agui/run/{agentId}` 入口。Web 客户端通过 Conversation Scope 下的 CrewScope API 调用 Personal Agent；服务端在模型执行前完成 Authentication、Membership、Participant、Conversation、Personal Agent、AgentRuntimeSession 和 ProviderBinding 解析。

客户端只提交消息内容。客户端提供的 path/header Agent ID，以及 body 中的 `threadId`、`runId`、Tool、Context、State、ForwardedProps、Principal、Role、ProviderBinding、Connection 和 Session 均不参与调用、授权和状态定位。未知控制字段在 DTO 解析阶段失败；Bridge 使用服务端事实重新构造 AgentScope 输入和 RuntimeContext。

受控 Bridge 固定以下配置与来源：

- `ToolMergeMode.AGENT_ONLY`，客户端 Tool 不进入 Agent Toolkit；
- `emitStateEvents(false)`，内部 Agent State 不进入 Web 协议；
- `emitToolCallArgs(false)`，Tool 参数不进入 Web 协议；
- `enableReasoning(false)`，`ThinkingBlock` 不转换为 AG-UI Reasoning 事件；
- AG-UI Thread/Run ID 由服务端生成；
- AgentScope `userId/sessionId` 来自持久化 AgentRuntimeSession 的版本化 Session Key；
- RuntimeContext 的身份、Scope 和 ProviderBinding 使用服务端类型化上下文；
- 缺失、停用、跨 Scope 或不一致绑定在模型执行前失败关闭。

AG-UI `RUN_STARTED` 可以携带协议输入快照。受控 Bridge 构造的快照不得包含客户端 Tool、ForwardedProps、Principal、Credential、Connection、ProviderBinding 或内部授权事实。完整边界与源码验证见 [M2-S01 受控 AG-UI Bridge 验证记录](../spikes/M2-S01-受控AG-UI-Bridge验证记录.md)。

### AgentScope 事件映射与披露

AgentScope 原始事件先通过显式白名单，再进入框架无关 `ExecutionEvent`。顶层公开文本可以映射；Thinking、Tool 参数与原始结果、Data、Metadata、Custom、State 和子 Agent 内容不能跨越 Adapter。官方 AG-UI Adapter 的输出继续通过服务端 `AguiEventSanitizer`，Tool/Message ID 不透明化，Tool Result Content、原始 Run Result 和 Provider Error 被移除或替换为安全值。

`ExecutionEvent` 按独立 Segment 验证 Invocation、连续序号、首事件和唯一终态。完全相同的历史事件重放不重复产生下游副作用；冲突重放、缺口与终态后事件失败关闭。公开文本和 Bean Validation 通过的 `TaskIntentV1` 只在 `COMPLETED` 后产生数据库事务 Candidate。完整协议见 [ADR-013](ADR-013-AgentScope事件映射与披露协议.md)，验证见 [M2-I06](../testing/M2-I06-AgentScope事件映射与脱敏.md)。

TaskIntent Candidate 使用 Invocation 与 Segment 派生稳定 Aggregate ID，在 `RUN_FINISHED` 对客户端可见前提交 DRAFT、READY、`TASK_INTENT_PROPOSED`、Conversation Event 与 Outbox。相同 Candidate 重放不新增事实；稳定 ID 对应不同 Scope、Conversation、Agent 或 Proposal 时失败关闭。人工完整修订产生 `TASK_INTENT_REVISED`，拒绝产生 `TASK_INTENT_REJECTED`；三个 Payload 通过类型化 Conversation 归属接口进入同一耐久 Conversation 流，不从任意 JSON 或 Aggregate ID 推断 Conversation。修订的 `READY -> DRAFT -> READY` 两次版本推进与事件、Outbox、CommandReceipt 位于一个事务。

### 结构化意图与澄清恢复

`TaskIntentV1` 与 `ClarificationRequestV1` 是不可信模型输出，依次通过三层边界：

```text
AgentScope JSON Schema
  -> CrewScope Bean Validation
  -> 当前 PostgreSQL 事实与 Domain Validation
```

AgentScope 自动生成的 JSON Schema 负责其实际声明的类型、Required 和嵌套形状；ToolValidator 也支持 Schema 中显式存在的长度、Pattern、Enum 与数组边界。AgentScope 2.0.0 不会把 M2 DTO 的 Jakarta Validation 注解完整转换为这些 Schema 关键字，因此 Bean Validation 必须再次执行 CrewScope DTO 约束；Application/Domain 再负责 Project 状态与 Scope、Principal/Membership、职责分离、归一化重复项、当前 Proposal、聚合版本和终态。任一层失败都不能创建或修改 TaskIntent、WorkItem 与责任事实。

Personal Agent 通过平台内置只读 `request_clarification` Tool 发起结构化澄清。Tool 输入包含 `ClarificationRequestV1` 和由 Bridge 写入的受约束 `answers`；首次调用固定返回 `ASK`，由 AgentScope 产生 `RequireUserConfirmEvent` 与 `RequestStopEvent(PERMISSION_ASKING)` 并保存 Pending Tool。

AgentScope 2.0.0 Resume 只消费 `Msg.METADATA_CONFIRM_RESULTS`，不会把确认消息正文加入模型上下文。客户端因此只提交澄清回答；Bridge 校验当前 Pending Clarification 后，以原始 ToolUseBlock 为基线构造带回答的 `ConfirmResult`，不接受客户端 Tool、Tool Name、Tool Input、PermissionRule、replyId 或 Session 覆盖。恢复后 Tool 将规范化回答作为 Tool Result 送回模型，模型再生成 `TaskIntentV1` Structured Output。

重复、过期和错配 Resume 在进入 AgentScope 前按 [ADR-007](ADR-007-API命令与并发协议.md) 裁决。完整源码与 Fixture 验证见 [M2-S03 结构化意图与澄清恢复验证记录](../spikes/M2-S03-结构化意图与澄清恢复验证记录.md)。

### 顺序与幂等

- 消费者按 eventId 幂等；
- Outbox 按 Topic 和分区键保持活跃事件顺序；
- 聚合投影按 aggregateVersion 检测缺口；
- 缺口触发延迟重试或从领域事实重建；
- Cursor 是流内位置，不作为全局事务顺序；
- Schema 版本按 eventType 独立演进并保留向后读取能力。

### Conversation Event 恢复协议

Conversation 状态、DomainEvent、Outbox 和 `conversation_event` 流索引在同一事务提交。流索引保存单调 `position`、稳定的 Conversation Stream `eventId` 和源 `domainEventId`；参与者等非 Conversation 聚合事件在写入时显式关联所属 Conversation。`conversation_event` 是可由 DomainEvent 重建的耐久投影索引，不替代领域事实源。

Conversation Event 历史按 `position ASC` 读取。HTTP JSON API 返回当前页、`hasMore` 和最后一条已返回事件的 Cursor；SSE 使用相同查询，并把该 Cursor 写入 SSE `id`。客户端重连时通过 `Last-Event-ID` 或 `after` 恢复，两个位置同时存在时必须一致。Cursor 使用版本化 Base64URL 编码，并绑定 Organization、Team、Conversation、Position 和 Stream Event ID；跨 Scope、跨 Conversation、非规范编码和不一致位置失败关闭。

服务端先完成一次带可见性校验的历史读取，再建立 SSE 响应。后续按最后成功发出的 Cursor 串行查询耐久流：一页事件完全交给下游后才推进下一页，追平后进入低频轮询。背压只允许合并空轮询信号，不允许丢弃业务事件。每次轮询重新验证当前 Membership、Participant 生命周期和历史可见截止时间，因此退出后的成员不会继续取得新事件。

Stream Event ID 由 `streamType + domainEventId` 稳定派生；同一 DomainEvent 的 Conversation 与 Team 投影具有不同 `eventId`，但保持相同 `domainEventId`。同一流按 `eventId` 去重，跨持久流按 `domainEventId` 合并，AG-UI 瞬时事件只按自己的 `eventId` 去重。Cursor 只负责流内恢复，不参与跨流去重。

当 Cursor 指向的投影位置已经被保留策略清理，服务端返回 `410 cursor_expired`。M2 不自动清理 Conversation Event；该错误契约用于管理员执行保留期压缩及后续归档实现。非法或跨流 Cursor 返回 `400 invalid_cursor`。

## 结果

- 三条实时流可以关联、去重和恢复；
- Outbox 可以从 M0 开始支撑后续 Audit 与投影；
- 前端拥有确定的写入确认协议；
- AG-UI 与业务事实的职责清晰。

## 验证

1. 事务回滚时没有孤立 DomainEvent 或 Outbox；
2. 重复 Outbox 投递只生成一份有效投影；
3. 乱序事件触发版本缺口处理；
4. 前端断线后通过 Cursor 补齐事件；
5. 同一 DomainEvent 在 Conversation 与 Team 流中可以去重关联；
6. Projection 重建不修改领域事实；
7. 当前 JSON 精确契约、旧事件缺失可选字段和未来新增未知字段均可读取；
8. 非对象 Payload、非法 UUID、非法 SchemaVersion 和负 aggregateVersion 被拒绝。

## 重新评估条件

- Outbox 吞吐需要独立消息中间件；
- 引入 Kafka/Pulsar 和全局事件分区；
- 跨区域部署需要全局顺序或冲突解决；
- AG-UI 协议升级提供统一持久事件语义。
