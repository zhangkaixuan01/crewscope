# M7-I03 本地密码编码与安全升级

> 任务：`M7-I03`
> 日期：2026-08-28
> 结论：通过

## 1. 实现边界

M7-I03 增加独立的 `LocalCredentialStore` 受信端口。通用账号 Repository、`CurrentAccountSnapshot` 和审计读取仍只能访问 `local_credential_metadata`，不返回 `password_hash`。JDBC Store 原子创建 Credential，并使用 `(id, account_id, version, credential_version)` Compare-And-Set 同时推进 Hash、算法、Credential Version、乐观锁版本和修改时间。

本地密码编码与 Bootstrap Basic 使用两个具名 `PasswordEncoder`：Bootstrap 保持既有 Delegating BCrypt 行为；本地 Credential 固定使用 Bouncy Castle 1.79 与下列当前 Writer：

```text
{argon2id}$argon2id$v=19$m=32768,t=3,p=1$
salt = 16 byte
hash = 32 byte
```

Reader 只接受当前 Argon2id、M19/T2/P1、M32/T2/P1 和 cost 10–12 的 BCrypt。未知算法、损坏形状、算法坐标不一致和不可认证 Account 都切换到进程启动时准备的当前参数 Dummy Hash。输入预算有效的每次失败认证只执行一次真实或 Dummy `matches`；错误密码、Dummy 路径和损坏 Hash 不触发 Rehash。

## 2. 准入与异步边界

`PasswordHashAdmissionExecutor` 使用公平 Permit、独立守护线程池和有界公平队列。调用方立即得到 `CompletionStage`，WebFlux Event Loop 不执行或等待内存困难 Hash。队列等待固定最多 100 ms；超时或队列满时不启动 Hash，返回无账号坐标、无密码和无 Hash 的 `PasswordHashCapacityException`，后续 HTTP 边界统一映射为 `429 too_many_requests` 与 `Retry-After: 1`。应用关闭时显式拒绝尚未开始的排队任务，Hash Provider 即使抛出 `Error` 也会将对应异步结果置为失败，不留下永不完成的请求。

部署通过 `CREWSCOPE_PASSWORD_HASH_PERMITS` 选择 Permit：2C2G 使用 2，8C16G 使用 4。配置小于 1、超过可用处理器数或超过 8 时启动失败。

## 3. 安全 Rehash

成功匹配历史 Argon2id 或 BCrypt 后，Writer 在同一受控 Hash 任务内生成当前 Argon2id，并以认证时读到的双版本执行 CAS。CAS 成功返回 `REHASHED`；并发改密或其他 Credential 轮换先提交时返回 `SKIPPED_CONCURRENT_CHANGE`，认证结果仍成功，但旧密码产生的 Hash 不重试、不覆盖新 Credential。当前参数返回 `NOT_REQUIRED`。

密码输入、编码 Hash、Hash 解析原因和 JDBC 的 Secret-bearing cause 不进入字符串表示、异常、日志、事件、指标或公开结果。`LocalCredentialAuthenticationMaterial` 与 `LocalPasswordHash` 的字符串表示始终脱敏。
