# M0-D03 V2 身份与平台基线

> 模块：`crewscope-infrastructure`  
> 迁移：`V2__identity_and_platform_baseline.sql`  
> PostgreSQL：`17-alpine`  
> 验证日期：2026-08-06

## 1. 目标

V2 建立 CrewScope 的可信身份、团队授权、追加写审计、事件投影游标和开发环境密文凭证存储基线。
数据库在 Organization 边界内校验关联关系，所有对象位于 `crewscope` Schema。

## 2. 新增表

| 表 | 职责 | 核心约束 |
|---|---|---|
| `principal` | 统一表示 User、Personal Agent、Team Agent、Specialist Agent 和 Service | 类型、可见性、状态、外部身份唯一、Owner 与 Team 同组织 |
| `team_member` | 保存用户在 Team 中的稳定成员身份 | Team/User 同组织、Team 内 User 唯一、成员状态和加入方式 |
| `team_role` | 保存内置和自定义团队权限集合 | Team 内 Role Key 唯一、Permissions 为 JSON 数组、Team/WorkProject Scope |
| `team_member_role` | 保存成员角色授权事实 | Member/Role/Grantor 同 Team、项目 Scope 受外键保护、有效授权唯一 |
| `audit_event` | 保存安全与治理的追加写投影 | Initiator/Actor/Agent 分离、DomainEvent 幂等、授权与 Payload 为 JSON 对象 |
| `event_projection_checkpoint` | 保存投影分区处理位置 | Organization/Projection/Partition 复合主键、事件游标完整性、乐观锁 |
| `credential_secret` | 保存开发与 Team Beta 的密文凭证 | AES-256-GCM、12 字节 Nonce、16 字节 Tag、Subject 形状和密钥版本 |

`credential_secret` 只包含 Ciphertext、Nonce、Authentication Tag、Key ID、Algorithm、AAD Version 和
Metadata。表中没有明文、Token 或 Secret Value 字段。

## 3. V1 增强

V2 对 V1 对象追加：

- `workspace.owner_principal_id` 的 Organization 级 Principal 外键；
- `domain_event.actor_id` 的 Organization 级 Principal 外键；
- Organization、Team、Workspace、WorkProject、WorkItem 的创建和最后修改 Principal；
- `outbox_event.version` 和 `updated_at`；
- Organization、Team、Workspace、WorkProject、WorkItem 的版本、时间和非空文本约束；
- DomainEvent 的事件字段与 JSON Payload 约束；
- DomainEvent 的 Organization 级幂等键部分唯一索引；
- Team、Workspace、WorkProject、DomainEvent 的租户组合唯一键。
- Workspace、WorkProject、WorkItem 和 DomainEvent 的 Organization/Team/Workspace 复合 Scope 外键；
- WorkItem `updated_at + id` Keyset 查询所需的团队状态和项目状态索引。

V1 文件保持原有内容和校验和。全部增强通过 V2 前向追加。

V1 中已有的 `workspace.owner_principal_id` 和 `domain_event.actor_id` 会生成同 UUID、同 Organization 的
`DISABLED` 占位 Principal。占位身份保留历史引用且不获得权限，后续身份对账负责补充外部身份并激活。

## 4. 安全与一致性边界

### 4.1 租户隔离

Organization 级组合外键同时携带 `organization_id` 和目标 ID。团队工作对象继续携带 Team 和
Workspace：Workspace 不能引用其他 Organization 的 Team，WorkProject 不能引用其他 Scope 的
Workspace，WorkItem 不能组合不同 Organization、Team、Workspace 或 WorkProject。跨范围的
TeamMember、Principal Owner、Workspace Owner、WorkItem、DomainEvent、Audit Actor 和 Credential
Subject 写入失败。

### 4.2 TeamRole 授权

TeamMemberRole 同时校验：

- TeamMember 与 TeamRole 属于同一 Organization 和 Team；
- Grantor Principal 属于同一 Organization；
- 授权 Scope 与 TeamRole 定义一致；
- `WORK_PROJECT` Scope 指向同一 Team 的 WorkProject；
- 同一 Member、Role 和 Scope 只有一个 `ACTIVE` Grant；
- 历史 `REVOKED/EXPIRED` Grant 保留。

### 4.3 Audit 与 Projection

AuditEvent 区分 Principal、Initiator、Actor、Agent 和 Credential Subject。一个 DomainEvent 最多生成一条
有效 AuditEvent。ProjectionCheckpoint 使用版本字段进行并发更新，并将最后事件限制在同一
Organization。

成员或 Agent 可修改的业务快照使用 `created_by_principal_id` 和 `updated_by_principal_id` 保存当前行
来源，包含 Organization、Team、Workspace、WorkProject、WorkItem、Principal、TeamMember、TeamRole、
TeamMemberRole 和 CredentialSecret。组合外键保证操作者属于同一 Organization。历史升级和系统修复
允许空值，新 Command 由应用层强制写入可信 Principal。

Organization 与首个 Principal 存在引导依赖，Organization 的两个操作者外键延迟到事务提交时校验，
支持在一个事务中先创建 Organization，再创建首个 Principal。DomainEvent、AuditEvent、Outbox 和
ProjectionCheckpoint 不增加通用业务操作者字段。

业务归档、取消、离开、移除、撤销和过期由状态表达。V2 不增加 `is_deleted`、`deleted_at` 和
`delete_reason`，删除原因由 AuditEvent 保存结构化 Reason。

### 4.4 CredentialSecret

Credential Subject 支持 `ORGANIZATION/TEAM/PRINCIPAL`。数据库校验 Subject ID 与对应范围字段一致。
连接引用在 V6 创建 Connection 表后补充外键；M0 使用 `connection_ref` 保留稳定标识。

## 5. 集成测试

测试类：

```text
V2IdentityPlatformMigrationIntegrationTest
```

五个 PostgreSQL 集成测试覆盖：

1. 空库执行 V1、V2，七张表只出现在 `crewscope`；
2. 必要索引及排序方向、已验证外键和 `ON DELETE RESTRICT` 删除语义；
3. Organization 与首个 Principal 在同一事务内完成可信引导；
4. 合法身份—成员—角色—事件—审计—投影—凭证数据链，以及业务快照操作者、核心工作对象复合 Scope、
   跨租户、重复授权、非法 JSON、非法授权 Scope 和非法加密参数拒绝；
5. 带 Organization、Team、Workspace、WorkProject、WorkItem、DomainEvent 和 Outbox 数据的 V1
   数据库升级到 V2，原业务数据保持不变，历史 Owner/Actor 生成禁用占位 Principal。

M0-D02 的三个迁移测试同步执行真实 V1→V2 升级和非默认 `search_path` 路径。
