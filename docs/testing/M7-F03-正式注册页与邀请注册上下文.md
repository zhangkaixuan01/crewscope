# M7-F03 正式注册页与邀请注册上下文

## 1. 交付结果

M7-F03 已完成正式 `/register`，并与 M7-A01 注册事务、M7-A02 匿名 Session、M7-A06 浏览器安全边界对齐。页面支持 `OPEN / INVITE_ONLY / DISABLED` 三种 Registration Mode；普通注册成功进入 `/onboarding`，带邀请注册在服务端原子创建 Membership、消费邀请后直接进入 `/conversation`。

登录页在 `OPEN` 模式显示“创建账号”入口，`INVITE_ONLY` 只说明新成员通过团队邀请加入，`DISABLED` 不暴露无效注册链接。已认证 Session 进入注册页时直接返回 Conversation。

## 2. 注册与邀请边界

注册字段固定为：

```text
username, email, displayName, password, invitationToken?
```

`HttpIdentityGateway` 只发送上述字段、单值 `Idempotency-Key` 和 Session 提供的 CSRF Header/Token，并通过响应白名单重建账号、Principal、Organization、可选 Team/Member、Onboarding、Receipt 与重放坐标。Team 与 Member 必须同时存在或同时为空，且必须与 `onboardingRequired` 一致；不一致响应失败关闭。

邀请注册使用 `/register#token=...`。页面只接受单个 `token` 参数和固定 43 字符 Base64URL 值，读入组件内存后立即用 Router Replace 清除 Fragment。Token 不进入 Query、普通 Store、LocalStorage、SessionStorage、Telemetry、错误文案或页面文本；组件卸载和成功提交后主动清空内存引用。`DISABLED` 连邀请注册一起关闭，`INVITE_ONLY` 在没有邀请上下文时不展示表单。

服务端对邀请不存在、过期、撤销、并发已消费和模式不允许统一返回 `registration_unavailable`。前端只呈现“当前无法创建账号”，不披露邀请是否命中或具体失效原因。用户名或邮箱冲突统一为“用户名或邮箱暂不可用”，不指出冲突字段。

## 3. 密码、幂等与恢复

注册密码在页面内按 12–128 Unicode code point 和 512 UTF-8 byte 双预算验证，HTML 输入保留 512 code unit 传输上限，避免把代理对误计为两个策略字符。服务端继续负责非法 Unicode、常见密码和最终领域策略。

一次用户提交意图生成一个 `crypto.randomUUID()` Idempotency Key。Pending 期间禁用字段和主按钮，Enter 与按钮重复提交只产生一个请求。以下结果不确定或提交后 Session 未建立的状态保留同一 Key：

- 浏览器网络失败；
- 客户端请求超时；
- `registration_session_unavailable`。

用户修改任一注册字段后废弃恢复 Key；明确的字段冲突、限流、无效请求和服务拒绝使用下一次提交意图。页面不记录密码、邀请 Token、CSRF 或 Idempotency Key。

## 4. 交互与可访问性

桌面端用户名与邮箱并列，展示名、密码与主动作跨满两列；390px 窄屏全部切换为单列且无横向溢出。注册字段使用原生 `autocomplete=username/email/name/new-password`，邮箱使用 `type=email` 与 `inputmode=email`。

普通表单聚焦用户名。Session Loading、Session 失败、注册关闭、仅邀请和邀请不可用状态各自拥有单一主标题；不可继续状态聚焦标题。注册错误使用 `role=alert` 摘要并迁移焦点，键盘顺序只依据 DOM，不使用正 `tabindex`。密码指导颜色经真实浏览器 Axe 检查调整为满足 WCAG 2 AA 的深绿色。
