## 1. 交付目标

M6-D03 建立固定模板协作通知的领域与应用契约：

- 版本化 `NotificationTemplate` 与精确变量 Schema；
- 成员 `NotificationPreference` 与 Inbox 来源 `NotificationIntent`；
- `POLICY_PREAUTHORIZED` Authorization Snapshot；
- 类型化 `NOTIFY_COLLABORATION` Action 参数；
- Delivery/Receipt 状态机、自动去重、授权漂移失效和人工再次投递；
- M5 GitHub Action 与 Notification Action 的执行边界。

本任务只定义 Provider 无关的通知核心。Lark Tenant、Member Mapping 和 Collaboration Recipient 在 M6-D04 实现，数据库表在 M6-D08 实现，Worker Claim、Lease、Fencing 和 Provider 调用在 M6-I03 至 M6-I06 实现。

## 2. 固定模板与变量边界

`NotificationTemplateRef` 精确绑定 Template ID 和正整数 Version。应用层 `NotificationTemplateCatalog` 只接受当前 `PUBLISHED` 版本，未知、已退役和已被新版本替代的引用全部失败关闭。

模板只保存服务端 Registry Key 与变量 Schema，不接受客户端正文。Schema 的变量集合必须与请求变量集合完全相等，缺失变量和未知变量均被拒绝。当前变量类型为：

| 类型 | 校验 |
|---|---|
| `TEXT` | 非空、长度上限、控制字符限制 |
| `TRUSTED_LINK` | TEXT 校验、HTTPS、精确 Scheme/Host/有效 Port Origin、无 UserInfo、无 Fragment |

验证后的变量按名称排序并使用长度前缀规范编码，生成 `NotificationVariableHash`。任意正文、原始 DomainEvent Payload、Agent 输出和 Provider Body 均无法进入 `NotifyCollaborationActionParameters`。

## 3. Preference 与 Intent

`NotificationPreference` 精确绑定 TeamMember、允许的 Inbox ItemType、启用状态、可选 `mutedUntil` 和 Version。每次计划和再次投递均读取当前偏好：

```text
ALLOWED  -> 立即 READY
DEFERRED -> notBefore = mutedUntil
DENIED   -> 拒绝创建 Action 与 Delivery
```

`NotificationIntent` 只能从 `OPEN` InboxSource 创建，保存稳定 Intent ID、Organization、Team、Recipient Member、完整 SourceKey、Projection Generation/Schema、精确 TemplateRef 和已验证变量。Intent ID 由稳定 InboxItem ID 确定性派生，影子重建不会形成重复意图。

## 4. 策略预授权快照

`NotificationAuthorizationSnapshot` 使用 `POLICY_PREAUTHORIZED`，完整绑定：

```text
Notification Intent ID
Inbox Source identity / revision
Template ID / Version
canonical Variable Hash
Recipient Mapping ID / Version
Provider Binding ID / Version
Connection ID / Version
Connection Grant ID / Version
Team Notification Policy ID / Version
Member Preference Version
Deduplication Key
```

字段使用版本化长度前缀编码并生成 SHA-256 Digest。自动投递使用 `automatic` 去重命名空间；人工再次投递使用 `originalDeliveryId + commandId` 命名空间。Template、Variables、Recipient、Binding、Connection、Grant、Policy 或 Preference 任一坐标变化都会得到新 Digest。旧非终态 Action 和 Delivery 使用稳定 InvalidationReason 进入 `INVALIDATED`，并保存不可变终态 Receipt。

## 5. Action 执行边界

共享 `ActionKind` 增加 `NOTIFY_COLLABORATION`，共享 `ActionParameters` 增加不含自由正文的 `NotifyCollaborationActionParameters`。通知使用独立 `NotificationPlannedAction`，固定风险为 `LOW_RISK_WRITE`，授权模式固定为 `POLICY_PREAUTHORIZED`，不创建可空 Confirmation。

边界采用双向失败关闭：

- M5 `ActionBundle` 拒绝 `NOTIFY_COLLABORATION`；
- M5 Action Worker、Reconciliation Worker 和 ActionReceipt 拒绝 Notification Action；
- Notification Planner 只创建 `NOTIFY_COLLABORATION`；
- `PUSH_BRANCH` 与 `CREATE_DRAFT_PR` 继续使用 M5 ActionBundle、Gate Review 和 Human Confirmation。

## 6. Delivery 与 Receipt

Delivery 状态机为：

```text
READY -> RUNNING
RUNNING -> RETRY_WAIT | UNKNOWN | SUCCEEDED | FAILED_FINAL
RETRY_WAIT -> RUNNING
UNKNOWN -> RECONCILING
RECONCILING -> RETRY_WAIT | SUCCEEDED | FAILED_FINAL
任意非终态 -> INVALIDATED
READY | RETRY_WAIT -> CANCELLED
```

每次状态迁移提交精确 Expected Version。重复 Start、陈旧 Version 和非法迁移均失败关闭。Timeout 或响应丢失进入 `UNKNOWN`，查询恢复前不能再次执行外部写入。

`SUCCEEDED`、`FAILED_FINAL`、`INVALIDATED` 和 `CANCELLED` 都保存唯一不可变 Receipt。成功 Receipt 保存 Provider Receipt 安全 Hash、Message ID Hash、`ACCEPTED` 和稳定 Evidence Code。最终失败只保存稳定 FailureCode 和 Evidence Code。Provider Body、Token、Endpoint、原始错误和 PII 不进入 Receipt。

## 7. 去重与再次投递

自动计划使用 Authorization Snapshot 的 Deduplication Key 确定性派生 Action ID 与 Delivery ID。相同 Intent 和相同授权事实的重复投影、Outbox 重放与调度返回同一 Plan。

再次投递要求：

1. 原 Delivery 为 `FAILED_FINAL`；
2. 命令携带精确 Delivery Version；
3. Actor 是当前 Organization 和 Team 内的 ACTIVE Recipient Member；
4. 当前 Template、Recipient、Binding、Connection、Grant、Policy 和 Preference 全部重新解析；
5. 新 Command ID 创建新的 Deduplication Key、Action、Delivery 和 `redeliveryOf`；
6. 相同 Command ID 在重新校验当前 Recipient Member 权限后返回同一 RedeliveryRecord；
7. 不同 Command ID 表示明确的新外部发送；
8. 原 Action、Delivery 和 Receipt 保持不可变。

Repository 契约要求 Plan 与 Redelivery Command Receipt 原子保存，并使用 Deduplication Key 和 Command ID 唯一约束收敛并发竞争。
权限已撤销时 Receipt 回放失败关闭，不因首次执行曾经成功而返回旧计划。
