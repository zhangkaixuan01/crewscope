# M8-I02：正式发行与镜像供应链

> 任务：`M8-I02`
>
> 状态：已完成（工作流与合同已实现，待真实受保护 Tag 验证）
>
> 目标版本示例：`v0.1.0-beta.1`

## 1. 交付结论

CrewScope 已建立 Tag 驱动的正式发行流水线：

- 只有匹配 `v*.*.*` 的受保护 Tag 触发 Release Workflow；
- Tag 对应的同一个 Git Revision 同时构建 Backend 和 Web，目标平台固定为 `linux/amd64`；
- 镜像推送到 GHCR，使用版本 Tag 和 `sha-<commit>` 辅助 Tag，部署坐标必须使用构建输出 Digest；
- `docker/build-push-action` 为两个镜像生成 SBOM 和最大级别 Provenance；
- Cosign 使用 GitHub OIDC keyless 对两个 Digest 签名，并在发布前立即验证签名证书身份和 OIDC Issuer；
- Release 附件包含 `release-manifest.json` 和签名验证结果，Manifest 固定应用版本、数据库 Schema、Tag、Revision、平台、Repository 与 Digest；
- GitHub Release 使用 `gh release create --generate-notes` 创建，已存在同名 Release 或签名验证失败时流水线失败关闭；
- Backend/Web Dockerfile 写入 OCI `version`、`revision`、`source` 标签，便于运行时核对部署镜像与源码 Revision。

## 2. GitHub 仓库要求

仓库需要启用：

1. GitHub Actions 和 GHCR Packages；
2. `main` 分支保护和 Tag 保护规则，Release Workflow 不允许从未审阅提交直接绕过 Main CI；
3. Actions 权限允许 `packages: write`、`id-token: write`、`attestations: write`；
4. 发布者具备创建 Tag 和 Release 的权限。

Workflow 使用短期 `GITHUB_TOKEN` 登录 GHCR，不保存长期 Registry 密钥。Cosign 不使用仓库中的私钥；签名身份由 GitHub OIDC 颁发并绑定到本仓库 Release Workflow 和具体 Tag。

## 3. 发布流程

```bash
git checkout main
git pull --ff-only
git tag -a v0.1.0-beta.1 -m "CrewScope v0.1.0-beta.1"
git push origin v0.1.0-beta.1
```

Workflow 依次执行：

```text
Tag/Revision 校验
  -> Maven clean verify 与 Configuration Metadata
  -> Web Coverage、Lint、Build、Histoire
  -> 配置/依赖/模块/Release 合同
  -> Backend linux/amd64 镜像构建 + Push + SBOM + Provenance
  -> Web linux/amd64 镜像构建 + Push + SBOM + Provenance
  -> Digest Cosign keyless 签名与证书验证
  -> 生成 release-manifest.json
  -> 创建 GitHub Release 并上传 Manifest/签名证据
```

本地只执行静态合同检查，不模拟 OIDC 签名：

```bash
node scripts/check-release-contract.mjs
node scripts/check-config-contract.mjs
```

## 4. 部署消费方式

从 GitHub Release 下载 `release-manifest.json`，核对 `revision` 与目标源码、`platform` 与主机架构、`databaseSchemaVersion` 与恢复边界，然后验证两个 Digest 的 Cosign 签名。将：

```text
images.backend.reference
images.web.reference
```

写入 `deploy/team-beta/.env` 的 `CREWSCOPE_BACKEND_IMAGE` 和 `CREWSCOPE_WEB_IMAGE`。生产 Compose 会拒绝缺少 `@sha256:<64-hex>` 的坐标；不要把版本 Tag 直接写入生产配置。

升级顺序：

1. 使用当前版本创建 Release 备份；
2. 拉取并验证新版本两个 Digest、SBOM、Provenance 和签名；
3. 只修改 Operator 环境文件的镜像 Digest、`CREWSCOPE_GIT_REVISION` 和应用版本；
4. `docker compose pull` 后执行 `up --detach --wait`；
5. 检查 API/Worker/Web Readiness、数据库 Flyway 版本、System Info 和关键业务 Smoke；
6. 失败时保留证据并使用已验证的旧 Digest 回退。数据库迁移不自动降级，Schema 不兼容时执行空目标恢复流程。

## 5. 供应链证据

每个 Release 至少保留：

- GitHub Actions Run URL 和触发 Tag；
- `release-manifest.json`；
- Backend/Web Digest、SBOM、Provenance 和 Cosign 验证输出；
- Main CI 与 Release Workflow 的测试报告；
- 发布后部署的 Environment Fingerprint、Schema Version 和 Smoke 结果。

证据不得包含 API Key、Token、Credential Key、模型正文、成员 PII、宿主路径或完整环境文件。Release Manifest 只保存公开镜像坐标和版本事实。
