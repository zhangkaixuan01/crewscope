# M9-A05：动作可用性验证（三类对象）

## 交付内容

- `WorkItemTransitionCatalog` 复用 `WorkItem` 的权威状态机边集合，仅补充动作标签、强弱级别和可撤销标记。
- `WorkItemTransitionAvailabilityProjector` 是**唯一**的可用性裁决体：详情端点取 `all(...)`（全量，含禁用项与原因），工作台取 `enabled(...)`（仅可执行），后者就是前者的过滤。
- `WorkItemAccessPolicy` 提供 `resolvePermission(...)`，返回一次读取成员角色与授权后的纯函数解析器；`hasPermission` 与解析器共用同一个权限判定体。
- 新增查询端点：
  `GET /api/v1/organizations/{organizationId}/teams/{teamId}/work-projects/{projectId}/work-items/{workItemId}/transitions/availability`
- 不可用动作保留在响应中，并返回稳定 `reason`。**当前只有 2 个原因可达**（`EXTERNAL_PROVIDER_MANAGED`、`PERMISSION_DENIED`）：`ARCHIVED` 与 `STATUS_NOT_ALLOWED` 因构造方式不可达，其余 4 个（`REVIEWER_REQUIRED`、`DUTY_SEPARATION_CONFLICT`、`GATE_NOT_PASSED`、`BLOCKED_BY_DEPENDENCY`）没有任何规则产出它们是尚未存在的产品规则，不是待接入的接线工作。逐条依据见 `docs/api/M9-状态流转可用性API契约.md` 的收口说明。
- 个人工作摘要（`GET …/work-desk`）的 `availableActions` 自本轮起填充为仅含 `enabled` 的动作对象数组，元素类型与上述响应复用同一个服务端响应类型。只有 WorkItem 行可能非空。
- `remedy` 在 **WorkItem 面**仍恒为 `null`：三处 `disabled(...)` 都传 `Optional.empty()`，本轮未改（Review 面已产出真实坐标，见下文「ReviewRequest 与 TaskExecution」一节）。

## 对账证据（反模式 #9）

`WorkItemTransitionAvailabilityReconciliationTest` 在（状态 × 原生/外部 × 有/无权限）全矩阵上把投影当作承诺、把命令当作权威：

- 投影说 `enabled` 的每一条边都真交给 `WorkItemCommandService.transition`，必须到达目标状态；
- 投影说 `disabled` 的每一条边都必须被命令拒绝，且拒绝原因与投影给出的 `reason` 对应；
- 每个格子另外断言「投影给出的边数等于状态机边数，且仅当原生且有权限」，因此两侧都不可能悄悄放宽。

该测试**不是空跑**，这一点是实测的：

- 删掉投影的权限分支（投影多许诺）→ 两个用例都失败；
- 删掉 `WorkItemCommandService.transitionInTransaction` 的来源守卫（命令接受本来被拒的边）→ 用例失败，且**这一次没有任何计数发生变化**，暴露它的只能是真的把边交给命令。这正是对账循环而非计数断言在起作用。

`WorkItemAccessPolicyM3A07Test` 另有九个格子的逐格矩阵，断言解析器与 `hasPermission` 一致，并同时断言一致的那个答案本身是对的。

## 数据库级证据

`JdbcWorkDeskRepositoryAdapterM9A05IntegrationTest` 是本仓库第一个工作台数据库级测试：真实 PostgreSQL（Testcontainers + Flyway 全量迁移）上运行工作台的 `WORK_ITEM` 与 `BLOCKED` 两条 SELECT，断言原生行与外部 Provider 行的 `transitionSubject` 正确、其余四个 section 无行、任何行都不带已裁决的动作。

它在接入当天就抓到一个编译期无法发现的缺陷：适配器曾写 `wi.source`，而 `crewscope.work_item` 自 V1 起的列名是 `source_provider`（`V6` 的 `ck_work_item_source_values` / `ck_work_item_source_reference` 都基于它）。缺陷已修，证据留在该测试里。

夹具不需要 `session_replication_role = replica` 绕外键：按迁移后的真实外键顺序插入 organization → principal → team → workspace → team_member → work_project 即可。

## 覆盖边界（如实记录）

- **非 WorkItem 行不带可用动作**这一条只在应用层被证明（`WorkDeskQueryServiceTest`）；`TASK_EXECUTION` / `REVIEW_REQUEST` / `HUMAN_GATE` / `INBOX` 行的 subject 缺席是 Java 侧字面量，SQL 层没有对应断言，数据库测试夹具也未播种这些行。
- 前端只做展示：`TodayPage.vue` 用 `primaryAction(...)` 按 `strength` 取第一条可执行动作；没有可执行动作时不渲染任何文案。工作台契约只返回启用项，前端若收到禁用项会按 `domains/workdesk/gateway.ts` 的严格映射风格抛 `TypeError`。
- 动作可用性仅用于前端发现，实际状态转移仍由命令服务独立执行完整校验。

## ReviewRequest 与 TaskExecution：另外两类对象（2026-09-17 收口）

上一版这个文档只覆盖 WorkItem 一类。本轮把另外两类补齐，三类对象现在**全部交付**，共用同一条线上形状（`AvailableActionResponse`）。

### 交付位置

| 对象 | 位置 | 形状 |
|---|---|---|
| WorkItem | 独立只读端点 `GET …/work-items/{id}/transitions/availability` + 工作台 `availableActions` 内联 | 端点返回全量（含禁用项，可解释）；工作台只返回 `enabled` 的动作 |
| ReviewRequest | 列表 `GET …/tasks/{taskId}/attempts/{executionId}/reviews` 与详情 `GET …/reviews/{reviewRequestId}` 各自内联 | 全量（含禁用项、原因与 `remedy`），顺序是固定的目录顺序，不是可用性过滤后的顺序 |
| TaskExecution | `GET …/tasks/{taskId}/attempts` 每个 attempt 内联 | 全量（含禁用项与原因），`targetStatus` 是**命令执行后的状态**而不是它内部请求的状态 |

三类都由同一个映射器产出线上对象（`AvailableActionResponse.of(...)`），因此"前端一套控件渲染三处"成立，也不可能序列化漂移。

### 原因可达性

- **Review 面**：`REVIEWER_REQUIRED`、`DUTY_SEPARATION_CONFLICT`、`STATUS_NOT_ALLOWED` 可达。`DUTY_SEPARATION_CONFLICT` 走的是 `ReviewerEligibilityPolicy.evaluateGate`（**Gate 授权**校验：当前 Gate Reviewer 不得持有该 WorkItem 上活动的 OWNER/EXECUTOR 责任），与 `TaskIntentProposal.requireDutySeparation`（**任务意图**校验）是两处不同的规则——上一轮文档把它们混为一谈，已更正。`PERMISSION_DENIED` 在这一面**不可达**：三个端点先要求 WorkItem 可见性，可见性不足时在投影之前就抛错，因此不存在"可见但无权限"的状态供投影标注。
- **Task 面**：`PERMISSION_DENIED`（不持有活动 OWNER/EXECUTOR 责任）、`GATE_NOT_PASSED`（attempt 停在只有人能决定的问题上：`WAITING` + 等待原因为 `CONFIRMATION`/`REVIEW`/`USER_INPUT`）、`STATUS_NOT_ALLOWED` 可达。`GATE_NOT_PASSED` 与 `STATUS_NOT_ALLOWED` 可执行的命令集合完全相同，差别只在措辞，由 `blockedReason` 一处产出。
- **`BLOCKED_BY_DEPENDENCY` 在三类面上都仍无规则**（需要 M11 的 `work_item_relation`），本轮不新增规则、零行为变更。

### `remedy` 的第一个真实生产者

Review 面 `REVIEWER_REQUIRED` 附带稳定站内坐标（`ReviewWorkbenchCoordinates.assignReviewer` 产出的 `/work?team=…&project=…&workItem=…&focus=…`），因此"无权限时为空而非指向不可达页面"这条验收项**首次有了正向与反向两类用例**。`DUTY_SEPARATION_CONFLICT` 与 `STATUS_NOT_ALLOWED` 刻意不给坐标（成员改不动），Task 面也不产出 `remedy`（同样改不动控制权或状态）——所以 `TransitionRemedy` 目前唯一的生产者仍是 Review 面的 `REVIEWER_REQUIRED`。WorkItem 面的 `remedy` 维持恒为 `null`。

### 同源与对账（反模式 #9）

- 裁决体各只有一份：WorkItem 是 `WorkItemTransitionAvailabilityProjector`，Review 是 `ReviewGateAvailabilityProjector`（声明式有序检查目录，每个检查读 `ReviewGateFacts`），Task 是 `TaskControlAvailabilityProjector`（四个动作的许可谓词**就是命令自己的前置条件** `TaskExecution::canRequestPause/canResume/canRequestCancel/canRetry`）。
- 重复的 Reviewer 资格判定被抽成一个领域类 `ReviewerResponsibility`，回收原先四个调用点各写一遍的实现；`ReviewDecision.requireAuthority` 的检查顺序据此调整为「资格先于分离」，投影与命令对同样的事实给同样的原因。
- 对账测试按对象类型各一份：
  - `ReviewGateAvailabilityReconciliationTest`：13 个矩阵格（状态 × Reviewer Agent 指派 × Gate Reviewer 指派 × 职责分离）× 4 个动作 = **52 次比对**，命令侧权威是三个真实服务。
  - `TaskControlAvailabilityReconciliationTest`：同样把投影当承诺、把 `MemberTaskCommandService` 当权威。
  - `WorkItemTransitionAvailabilityReconciliationTest`：见上一节。
- 非空跑证据（逐份说明，避免把"设计上不该空跑"当成"实测过"）：
  - WorkItem 面：见上一节的两处变异（投影删掉权限分支、命令删掉来源守卫）。
  - Review 面：三处变异，其中最有说服力的一次是**命令侧**的——把 `ReviewerResponsibility.holdsGateReviewer` 改成恒真（投影输出完全不变），只有真的把动作交给命令才会暴露：`decide @ open, no Gate Reviewer` 期望 `REVIEWER_REQUIRED` 却得到 `STATUS_NOT_ALLOWED`。
  - Task 面：两处变异，**投影侧与命令侧各一次**（收口时补做）。投影侧删掉 `evaluate` 的 `if (!authorized)` 分支（投影多许诺）→ 2 个用例全失败：`the projection offers the wrong controls at CREATED/observer ==> expected: <[]> but was: <[cancel]>`，另一条同时暴露措辞漂移 `expected: <PERMISSION_DENIED> but was: <STATUS_NOT_ALLOWED>`。命令侧把 `TaskControlAuthority.require` 改成空实现（`granted` 不动，因此**投影的所有输出逐字不变**）→ 用例失败：`the command must refuse the withheld control at CREATED/observer ==> Unexpected exception type thrown, expected: <PolicyDeniedException> but was: <InvalidStateTransitionException>`。两处变异均已还原（还原后该测试复跑退出码 0），且第二处只有真的把动作交给命令才会暴露——与 Review 面那条命令侧变异是同一个道理。

### 覆盖边界（如实记录）

- **Review 面的 `re-review` 启用方向只断言到「命令没有因投影给出的原因拒绝」**，不是「命令成功」：`re-review` 的 `successor` 迁移读前驱的聚合字段而非访问器，mock 前驱无法驱动它。夹具用 mock 的 `ReviewRequest`，聚合自身的状态迁移归 `ReviewRequestTest`。
- **Task 面的 `resume`/`retry` 还需要「一个被中断的 AgentRun 及其匹配的待决 interrupt」**，那是另外的聚合的事实；投影在 execution 事实允许时报可用，命令仍可能因缺少该运行时事实而拒绝。这条缺口写在 `TaskControlAvailabilityProjector` 的类注释里。
- **Review 面还有三条不可观察的前提**（ContextPackage 权威、精确活动的 Reviewer Specialist Session、当前 Diff/TestEvidence/PolicySnapshot），逐条理由见契约文档 §4.5。
- 「500 项无 N+1 / P95 劣化 ≤ 10%」与「并发状态变更下的投影时效」仍未交付实测证据，前者属 `M9-Q02`。本轮交付的是按构造消除 N+1 的计数式回归门：Task 面的责任读取在每个请求里**只读一次**并对同一 Task 的所有 attempt 复用，工作台同理。

逐条依据（含矩阵表的每一格）见 [M9 状态流转可用性 API 契约](../api/M9-状态流转可用性API契约.md) 第四、五节。
