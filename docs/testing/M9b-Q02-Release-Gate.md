## 3. 真实栈抓到并修复的产品缺陷（Q02 存在的直接证据）

1. **Inbox 收据外键 500**（`crewscope-infrastructure`）：`InboxDispositionCommandStore` 写命令收据时 `inbox_item_id` 外键失败——集成测试种子用裸 `UUID.randomUUID()` 直插，读侧 `InboxItemId.requireSource` 派生重验不过。修复：种子按 `InboxItemId.fromSource(...)` 同源派生（`InboxDispositionCommandStoreIntegrationTest` 2/2 绿）。属测试基建修复，生产行为无改动。
2. **首次委托预检死锁**（`crewscope-application`/`crewscope-server`/`crewscope-web`）：委托表单提交门控在「批准的预检」上，而预检端点只评估当前责任链——未分配 Agent 的「分配并启动」永远过不了自己的预检（RESPONSIBILITY_REQUIRED），首次委托死锁；mock 档直接 mock 预检结果从未暴露。修复：预检请求新增可选 `plannedExecutorAgentProfileId`，服务端 `withPlannedExecutor`（`assignExecutorIfRequested` 的 preview-only 镜像）把计划分配构造为瞬态责任合入评估链（同门禁、不落库、不发事件），前端 assign-and-start 模式随选择传该字段。回归：`AgentTaskCreationServiceA05Test` 新增 2 测试（9/9 绿）；契约文档 §9.2 补预检镜像说明（`docs/api/M9b-委托与工作摘要契约.md`）。
3. **会话深链被 scope 规范化吞掉**（`crewscope-web`）：AppShell 的 scope 规范化把「URL 未带 project→默认补全」当作 scope 切换，清掉了 `conversation` 深链参数——从 Inbox/书签/分享链接首次进入会话被弹回欢迎态。修复：以 store 中离开的 team（`previousTeamId`）区分真实切换与首次进入；默认补全不再清深链坐标。回归：`app-shell.spec.ts` 新增「project-less deep link」契约测试（双视口），既有「切换 Team 清深链」契约保持。
4. **设置页迟到的自动选择劫持配置返回链**（`crewscope-web`）：模型设置页加载后自动选第一个 Provider 并 `router.push`（写 provider/ownerType）；真实栈网络慢，成员点「返回工作项」离开后该 push 迟到到达，把页面拉回设置页且重建的 query 不再携带 `from`——F02 配置返回链被劫持，委托草稿无法回到原任务。`selectProvider` 的 `pageOwner.isCurrent()` 检查在 push 之后，拦不住卸载后的迟到调用。修复：push 前检查 `route.name !== 'model-settings'` 即放弃（M9b-Q02）。回归：`m9b-f02/configure-return.spec.ts` 8/8、`ModelSettingsPage.spec.ts` 等单测 22/22，真实栈 deploy t5 复验。
5. **预检 403 误触发 F05 清库，吃掉配置返回链上的草稿**（`crewscope-web`）：委托预检按冻结束合同以 `POLICY_DENIED → 403` 拒绝未配置模型的假想链，而 `apiClient` 把任何 403 都当作「身份失去权限」触发 `clearF05TeamScope`——真实栈网络慢，表单打开时的预检 403 迟到落在成员输入草稿**之后**，把委托草稿与 Coding 目标草稿一并清除（mock 档网络快，403 先落、输入后写，从未暴露；时序反向即丢草稿）。预检失败正是引导态与「去配置模型并返回」的输入，F05 的「撤权即清」语义不适用于预览类请求。修复：`ApiRequestOptions` 新增 `preview` 元数据（不进 Fetch init），五个预检网关（委托任务预检、Agent 模型预检、Coding 目标/仓库草稿/仓库绑定预检）携带该标记，`client.ts` 对 preview 请求的 403 不触发 forbidden sink；撤权矩阵（普通读 403 → 只清当前 Team）语义保持。回归：`client.spec.ts` 新增双契约（普通 403 触发 sink / preview 403 不触发且标记不泄漏）、`f05/local-trust.spec.ts` 与 `q01-revocation-matrix` 复验、真实栈 migration row5 草稿保留复验。
6. **迁移 row5 剧本缺通知前置**（`crewscope-web` e2e）：次日回访行断言 Inbox 归档/恢复/未读环，但单账号无模型剧本不产生任何 Inbox 条目（条目来自 RESPONSIBILITY_ASSIGNED/REVIEW 等事件投影，通知对象是被分配方）——此前该段从未真实执行到。修复：row5 在迁移者离开期间邀请一名 Team Lead 同事（页面邀请→受邀注册），同事接手载体工作项后把迁移者设为 EXECUTOR，产生真实的 RESPONSIBILITY_ASSIGNMENT 通知；归档/恢复/未读断言不变。附带裁定：MEMBER 即使持有工作项 OWNER 角色也无 `RESPONSIBILITY_MANAGE`（团队级权限），该边界由 collab-recovery 承担。
7. **全新 Worktree 的亚秒级「not a repository」窗口击穿全部 Coding 执行**（`crewscope-infrastructure`）：全新 provision 的 worktree 在共享文件系统（virtiofs）上存在亚秒级元数据可见性延迟——workspace 进入 ACTIVE 后约 96ms 的首次 RESET diff 必然命中 `git exit 129（not a git repository）`，`WorkspaceDiffException[COMMAND_FAILED]` 把执行打入 RECOVERING；恢复路径在数秒后执行时全部穿过，于是表现为执行反复停 WAITING(CONFIRMATION)/RECOVERING。取证用三层夹逼：宿主 50ms 高频重放（捕获「index 空+全 staged 删除」中间态）、容器内 1s 探针（worktree 自出现即 index 完整、rc=0）、JVM WARN（exit=129）——定位为初始窗口而非持续损坏。修复：`WorkspaceDiffMonitorFactory.initializeWithRetry`（`crewscope-infrastructure/.../workspace/repository/WorkspaceDiffMonitorFactory.java`）对 COMMAND_FAILED 做 ≤3 次 × 750ms 有界重试；RESET 是幂等重算，确定性错误（policy/budget/输出形状）立即失败。实测：修复后 PREPARING→RUNNING（无 RECOVERING）→CONFIRMATION→resume 202→工具会话（44 次调用）→模型真实落盘文件全程穿透。

### 3.1 实测边界与已解除边界（非缺陷，关闭条件按计划风险 6 回退）

- **（已解除）无网沙箱 × Maven 测试仓库的 COMPLETED 不可达**。Q02 前期 Coding 沙箱为 `network=none`（`--read-only`+cap-drop ALL 不变），Java/Maven 测试仓库（`zhangkaixuan01/crewscope`）在无网沙箱内 `mvn test` 需联网拉依赖，coding 执行最深终态为 `FAILED(TEST_REPAIR_BUDGET_EXHAUSTED)`。本包把沙箱网络升级为三档（见 §3 缺陷 12：默认 RESTRICTED_EGRESS，独立 egress bridge 可达 Maven Central，与 compose 内部网络隔离）后该边界解除：真实链路实测冷拉全量依赖+全 reactor 编译+定向测试 121s（6 CPU/6 GiB 运维 sizing、900s 命令上限内），t4 到达 COMPLETED 并交付 diff manifest；review 门与 Draft PR 深面随之打开（§1 第 3/5 行）。`node-24-npm-11` profile 的镜像 sha256 仍为全零占位不可用（不在本仓库栈型验证面内）。
- **deepseek-v4-flash 计划稳定性变量**：偶发 `TASK_PLAN_INVALID`（约 20 秒终态，模型未进工具会话）；t4 对「到达终态但无 diff manifest」做一次整体重试（该失败模式实测 20s，重试成本可控）。
- **422 REPOSITORY_INVALID 一次性事件**：诊断期某次 create 后 2 分钟内出现一次；此后同条件下手测全部通过、api 重启后未复现，静态穷尽（绑定/scope 四元组/属主/bare/容器内清环境复现）无解。定性瞬时环境事件（可能关联同 bare repo 恢复期操作），观测补丁 #3 保证复发可定位。
- **catalog 5 分钟发现缓存与交付计划的「当前事实」语义（非缺陷，spec 语义修正）**：仓库目录条目是 TTL=5 分钟的发现缓存（DB 实测），而 t4 真实模型执行 + t5 人审的全链耗时必然超过 TTL——`CurrentActionDeliveryPlanningResolver` 解析「当前」授权事实（`isCurrentAt`），过期即 422 `deliverable GitHub Repository Catalog entry is unavailable`。交付计划要求当前事实、过期即拒是正确语义（非平台缺陷）；成员交付已批准的变更前应重新同步授权视图，spec 在 t5 交付前补 `repositories/synchronize`（re-synchronize），计划即运行在新鲜目录行与连接版本上。
- **人审与交付链的三个 spec 语义修正（真实产品行为与初版 spec 假设的差异）**：① 人审 Gate 决策要求 **USER 型 Reviewer 座位**且与 Owner/Executor 分离（`ReviewerResponsibility.requireGateReviewer` / `ReviewerEligibilityPolicy`）——advisory agent reviewer 只产 findings，A 持有 OWNER 也不能自审，故 t5 由第二名真人成员 B 加入并接 gate-reviewer 座位（§1 第 5 行「人审与 PR」的双账号形态）；② review 列表行是摘要投影（finding 计数、latestDecisionType），decision id 只在 workbench 详情视图——断言 decisions 需读 detail 而非列表；③ 即上条的交付前 re-synchronize。
- **外部 WAN 瞬态面（直连形态实测，e2e 有界重试吸收）**：对 github.com 的首次导入 clone 观测到 TLS 中途断流（`SSL_read: unexpected eof`，91s 处）与吞吐 5 倍方差（直连好网 13s / 差网 67s+）；preflight 的上游 git probe 出现 ~5s 超时型 503（retryable，同刻大流量 clone 可成功）；synchronize 偶发 503。spec 侧对应吸收（终态断言强度不变）：导入一次有界重试（新 job 新 key）、preflight 3×15s 重试后仍败则边界 skip 注记、synchronize 一次 5xx 重试、settle 窗口覆盖平台 git 预算（5m）+方差。DeepSeek 晚高峰另见 `MODEL_TIMEOUT` 连发（模型流超时，执行终态 FAILED）——外部 Provider 状态，等待窗口重跑即可，非平台缺陷。
- **r14 观测已在 r27/r28 四次复现并定性（根因与建议根修见 §3 缺陷 24）**：`CommandEvidenceWriter` 的 `ArtifactStoreException ← FileLockInterruptionException` 是命令超时经线程中断投递后的连锁症状之一（中断位置上后阻塞 `FileChannel.lock()` 立即抛出），不是独立故障。r14 当时执行未中断、evidence 完整；r27 起（`16:04:01`、恢复轮 `16:22:57`）与 r28（`16:30:50`）三次均在命令起跑**整 300 秒**后被打断并升级为执行级终止。初判「外部 DeepSeek 传输降级」**有误**：`MODEL_TRANSPORT_ERROR` 出现在中断之后 19-21 秒（中断后的下一次模型调用失败），且 r27 恢复轮完全未出现——它是下游症状而非触发源。排除项：非 OOM（沙箱 813 MiB / 6 GiB 上限，全栈约 2 GB / 7.75 GiB Docker VM，无 oom/die 事件）、非模型流故障（观测补丁 #9 在失败窗口零输出）。
- **陈旧 dispatch 的静默等待是设计内行为（观测注记，移交 M10）**：缺陷 27 修复部署后，此前轮次遗留的 READY dispatch（其 bundle pin 住的 catalog/grant 事实已过 TTL）被复活的 worker 每秒重新评估——`ActionWorker.claimOne` 对 `resolveCurrent` 抛出的 DomainException 走静默 `continue`（行保持 READY、claim_attempts 不变、零日志；I11 注释明言「later current-fact changes can make it eligible again」）。行为正确（陈旧行等待事实刷新或人工清理），但「每秒评估一行数小时且零可观测痕迹」对运维不友好；建议 M10 对该分支补一条 secret-free WARN（含 dispatch id 与拒绝原因码）或计数指标。

### 3.2 观测修补（9 处 WARN 日志，均无行为改动，保留为长期观测面）

1. `TaskWorkerExecutionLoop`：捕获 `WorkspaceDiffException` 时打错误码（如 `[COMMAND_FAILED]`）。
2. `AgentScopeFailureClassifier`：打 safeCode。
3. `ManagedRepositoryBindingPreflightAdapter`：打 secret-free 的 preflight 拒绝原因（422 复发可定位）。
4. `GitWorkspaceDiffReconciler`：打 git error/exitCode/cause 类型（无路径、无原始输出）。
5. `GitHubRepositoryImportAdapter`：导入失败的异常类 + git 错误码 + exit code（导入路径原本零日志，$失败码一律 MIRROR_UNAVAILABLE$ 无法定位）。
6. `GitProcessRunner`：COMMAND_FAILED 时打首行 stderr（≤200 字符；ask-pass 程序永不回显秘密、URL 不携带凭据，命令元数据即无秘密）——缺陷 9 的实锤来源。
7. `CodingSpecialistStepRuntime`（`crewscope-agentscope`）：终态结果被 `validateCodeChangeResult` 拒绝时打被拒字段的消息（终态码 `CODING_RESULT_INVALID` 本身不含被拒字段，此前模型输出缺陷与平台事实缺失在该终态下不可区分）——缺陷 14 的实锤来源。
8. `ReviewerSpecialistRuntime.sanitizeModelFailure`（`crewscope-agentscope`）：reviewer 调用失败被包成 Safe 异常前打 safeCode + 异常类名 + root 类名（sanitization 会抹掉全部异常信息，49ms 无出站的失败原本不可归因）——缺陷 20 的实锤来源。
9. `ObservableAgentScopeModel`（`crewscope-agentscope`）：模型流终止打 classify 码 + cause 类名（缺陷 20 取证中证明失败不经模型流——该观测点无输出本身即证据，保留为模型流层长期观测）。

### 3.3 部署面调优（`deploy/team-beta/compose.yaml` api 环境，随本包交付）

- `CREWSCOPE_CODING_GIT_TIMEOUT=300s`（源默认 30s）：首次导入的 bare mirror clone 需搬运全量仓库历史，实测吞吐 13s（直连好网）到 260s+（代理差节点）方差 5 倍以上，30s 必然超时真实世界 clone；5m 对齐 `GitCommandPolicy` 上限，只放宽 git 命令预算、不动沙箱策略。
