## 1. 交付结果

M7-Q03 建立独立的一键生产 E2E 门禁：从空 PostgreSQL 与 Redis 数据卷启动 Team Beta 栈，执行 V1→V32 迁移和正式 Web 构建，再由两个互不共享 Cookie、Storage 与 Session 的 BrowserContext 扮演 Team Owner 和普通成员。门禁不使用 `page.route()`、内存 Repository、内存 Session 或数据库预置身份替代生产链路。

统一入口：

```bash
./scripts/m7-q03-two-user-e2e-gate.sh
```

门禁使用独立 Compose Project `crewscope-m7-q03`、独立运行目录 `var/release/m7-q03/team-beta` 和默认入口 `http://127.0.0.1:18080`。结束、失败或中断时只清理该 Project 的容器、网络和 Volume，不影响日常 Team Beta 数据。

## 2. 双用户权威链路

每个 Playwright Project 都从全新用户和 Team 开始，完整验证：

1. 用户 A 通过正式注册页创建 USER Account，并通过 Onboarding 创建 Team、Workspace、Owner Role Grant 和默认 Personal Agent；
2. A 从正式成员页创建 MEMBER 一次性邀请，用户 B 在独立 BrowserContext 中读取 Fragment 证明并注册加入；
3. A/B 的 Account、Principal、TeamMember、Cookie Session 与默认 Personal Agent 均不同，Team ID 相同；
4. A 具备 `team:members:manage` 与 `audit:read`，B 具备成员基础能力但不获得管理和审计能力；
5. A/B 都从服务端读取相同的两人 Membership 事实；
6. A 创建 TEAM Conversation 并添加 B，B 发送消息，A 从服务端消息流读到 B 的 Principal 身份与正文；
7. 两个页面刷新后分别恢复原 Account；API 容器重启后 Redis Session 仍恢复到各自 Account；
8. Audit 查询同时包含 A/B 两个 actorId；Redis 强制过期两个浏览器 Session 后，两页均进入带安全 `returnTo` 的正式登录页；
9. A/B 分别重新登录、恢复同一个 Team，再分别退出，最终 Session 均为匿名。

## 3. 真实生产栈修复

真实门禁发现并关闭了单元测试和 Mock E2E 未覆盖的部署/装配缺口：

- 邀请加入事务现在同时创建受邀成员的默认 Personal Agent，并与 Account、Membership、Role Grant、邀请终态原子提交；
- Redis URL 同时支持 Team Beta configtree Secret 与环境变量，不再误连容器内 `localhost`；
- Nginx 转发保留非默认端口，Origin、Host 与请求 URI 在 `18080` 下保持一致；
- 登录防护接受代理产生的 unresolved 数字 IPv4/IPv6 字面量，但不解析主机名或执行 DNS 查询；
- Session 将 TeamPermission 投影为唯一稳定浏览器能力键，普通 ACTIVE 成员获得基础读取能力；顶层只发布账号级能力，AuthStore 按当前 Team 切换 `teams[].permissions`，不会把其他 Team 的管理员权限并入当前 Scope，`operations:manage` 只来自持久化 `PlatformRole.OPERATOR`；
- 邀请服务与登录服务改用各自的部署属性开关装配，消除跨配置类 `@ConditionalOnBean` 扫描顺序导致的 404/503；
- Audit/Correlation Cursor Codec 对密钥环改为启动期强依赖，缺失时拒绝启动，不再发布运行时必然 503 的 API。
