# M1-D05：责任分配领域模型

> 日期：2026-08-07<br>
> 状态：已完成<br>
> 模块：`crewscope-domain`、`crewscope-application`

## 目标

建立 WorkItem 上的稳定责任事实，支持 Owner、Executor 和 Reviewer 分配，保证一个 WorkItem 只有一个有效 Owner，并为后续职责分离、API、数据库约束和时间线提供领域边界。

## 责任事实

`ResponsibilityAssignment` 保存：

```text
ResponsibilityAssignmentId
WorkItemScope / WorkItemId
OWNER / EXECUTOR / REVIEWER
Actor PrincipalId / PrincipalType
Actor TeamMemberId（USER 必填，Agent 为空）
ACTIVE / RELEASED
AssignedBy / AssignedAt / AcceptedAt
ReleasedBy / ReleasedAt
Version
AuditMetadata
```

M1 中的直接分配立即生效，`acceptedAt` 与 `assignedAt` 相同。Handoff 和 Takeover 在后续阶段先完成接受流程，再创建新的 Active Assignment。

Assignment 释放后进入 `RELEASED` 终态，记录释放人和释放时间，同时推进 Version 与 AuditMetadata。历史责任不覆盖、不复活。

## 主体资格

| 角色 | 允许主体 | 额外条件 |
|---|---|---|
| `OWNER` | USER | 必须对应同 Team 的 Active TeamMember |
| `EXECUTOR` | USER、PERSONAL_AGENT、TEAM_AGENT、SPECIALIST_AGENT | USER 必须对应 Active TeamMember；Agent 必须属于同 Team |
| `REVIEWER` | USER、SPECIALIST_AGENT | USER 必须对应 Active TeamMember；Specialist Agent 必须属于同 Team |

所有 Actor Principal 必须为 Active，与 WorkItem 属于同一 Organization，Team Scope 与 WorkItem 一致。分配操作人也必须是同 Scope 的 Active Principal。TeamRole 权限由应用用例在服务端解析，不接受客户端声明的权限事实。

Reviewer 与 Owner/Executor 的职责分离、Gate 效力和单人团队降级属于 M1-D06 `ReviewerEligibilityPolicy`。D05 不预先实现该策略。

## 分配与并发

- `ResponsibilityAssignment` 是责任事实源；WorkItem 不复制可独立修改的 Owner 事实。
- Owner 只通过替换用例变更，在一个事务内释放旧 Owner 并创建新 Owner，不提供单独释放 Owner 的入口。
- Owner 替换必须携带当前 Assignment ID 与 Version，同时防止旧版本和 Assignment 替换后的 ABA 覆盖；首次分配显式表示预期不存在 Owner。
- Executor 和 Reviewer 可以存在多个 Actor，同一 WorkItem、Role 和 Actor 不能存在重复 Active Assignment。
- Executor 和 Reviewer 释放必须携带 Assignment Version。
- Application Service 在事务内完成查询、版本检查、释放和创建。M1-D07 通过部分唯一索引裁决首次 Owner 并发创建，M1-D08 将索引冲突和乐观锁失败统一映射为稳定冲突。

## 阶段边界

M1-D05 实现 Domain Model、Application Port 和责任协调服务。本阶段不修改 Flyway 迁移，不实现 JPA Repository Adapter，不发布 API 和 DomainEvent。这些能力分别由 M1-D07、M1-D08 和 M1-A06 完成。
