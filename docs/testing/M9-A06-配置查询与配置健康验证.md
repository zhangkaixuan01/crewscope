## 已交付

- Agent 配置服务新增按 Revision 的只读读取，复用既有可见性与 Team 权限边界。
- 新增全量公开载荷接口，使用配置 hash ETag；历史 Revision 保持不可变，没有回滚或应用历史版本写路径。
- 新增配置健康派生服务与 `/configuration-health` 查询，统一从 Agent 配置、模型连接、CredentialStore 和 Provider Connection 读取事实。
- 健康响应仅返回稳定状态、reason、责任方和 action，不返回凭证明文、endpoint、宿主路径或外部原始错误。

## 收口修正（复核发现的接线缺陷）

A06 的两个投影（`configuration-health` / `configuration-search`）在服务端先行落地，但前端尚未消费；复核在这条链路上发现三处缺陷与一处词表事实，本轮一并修正：

| 项 | 事实 | 修正 |
|---|---|---|
| 搜索路由 | `ConfigurationSearchApplicationService` 发 `/settings/agents?agentId=<id>`，而前端 `domains/settings/route.ts` 读的是 `query.agent`，全仓库没有任何 `agentId=` 消费者，该深链是死的 | 服务端路由串改为 `/settings/agents?agent=`；前端本就有 `?agent=` 的消费方 |
| 工作台深链 | `JdbcWorkDeskRepositoryAdapter` 的 TASK_EXECUTION 分节发 `/work?team=…&project=…&taskExecution=<id>`，而 `/work` 只有收到 `task=` 才会打开 Task 详情，因此这条深链此前无法落地 | SELECT 增加 `task.id`，路由串补 `&task=<task_id>`；前端 `resolveTaskExecution()` 只在深链命名的执行确实存在于该 Task 时才采纳，否则回落到既有选择链 |
| 参数错误 | `ConfigurationSearchApplicationService.requireQuery` 抛裸 `IllegalArgumentException`，而 `ApiExceptionHandler` 只把 `DomainException` 映射到 `ApplicationErrorMapper`，所以空 `q` 或 101 字 `q` 会落成 **500 `internal_error`**，违反 A06 合同 | 边界校验放到 `crewscope-server` 的 `TeamSetupReadinessController`（`ApiRequestException(400, "invalid_request", …)`，应用模块依赖不到该异常类型），应用层的 `requireQuery` 改抛 `DomainValidationException("q", …)`，此后只是防御性前置条件 |
| actionKey 词表 | 同一页面上并存两套：就绪度用 `OPEN_WORKPROJECT_SETTINGS` / `START_GITHUB_IMPORT`，A06 配置健康用 `OPEN_MODEL_SETTINGS`；两者的并集才是前端可跳转的全集 | 本轮按并集解析并记录，不统一词表（统一属于契约变更，超出本轮范围） |

前端消费面（`M9-F10` ⑤⑨）：`SetupPage` 渲染配置健康四组件与明文降级说明；`SettingsShell` 的二级导航内按字段搜索并把命中项落到对应设置页；`member=` / `binding=` / `taskExecution=` 三个深链分别由团队成员页、受管仓库页与工作项页定位到对应行。新增 spec 覆盖网关映射、store 的单飞与代际丢弃、健康四态、搜索六态、深链命中与未命中。
