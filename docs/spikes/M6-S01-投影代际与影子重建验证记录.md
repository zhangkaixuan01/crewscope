# M6-S01 投影代际与影子重建验证记录

> 任务：`M6-S01`<br>

## 1. 验证目标

M6-S01 对照现有 Outbox Publisher、`IdempotentEventDispatcher`、`CheckpointedProjectionRunner`、Consumer Receipt 和 Audit 投影，验证：

1. 影子 Generation 从 DomainEvent 历史重建并在构建期间接收实时事件；
2. Consumer Receipt 和 Projection Checkpoint 按 Generation 隔离；
3. 多 Aggregate 重放按分区、版本、发生时间和 Event ID 确定排序；
4. 版本缺口和 Projector 失败不留下部分事务；
5. Count、规范 SHA-256、原子 Pointer 和 Fencing Token 可以管理切换；
6. Inbox 成员处置事实在投影重建外独立保留；
7. Cursor 绑定 Generation，切换后使用明确的过期契约恢复。

本 Spike 使用测试内 PostgreSQL Schema 和 JDBC Harness，不提前创建 M6-D07 生产领域对象、V27 迁移或 M6-E01 Generation-aware Runner。

## 2. 现有实现差距

M0 实现已具备分区 Aggregate Version 缺口检测、同版本确定排序、消费回执和本地事务。M6 重建需要补齐以下持久化边界：

- `CheckpointedProjectionRunner` 使用固定 Projection Name 和单代际 Checkpoint；
- `event_consumer_receipt` 不包含 Projection Generation；
- `InProcessEventTransport` 在进程启动时固定消费者列表；
- 在线投影没有 Generation Pointer、状态机、校验快照和 Fencing Token；
- Outbox 没有可作为历史重放截断点的全局单调高水位。

因此，实现顺序固定为“创建 BUILDING Generation 并接入实时消费—重放全部历史—规范校验—原子切换”。时间戳不用于截断历史。

## 3. PostgreSQL 验证模型

测试 Schema `m6_s01` 包含：

```text
source_event
projection_generation
projection_pointer
projection_checkpoint
projection_consumer_receipt
projection_row
member_disposition
```

`projection_generation` 限制单个 Active 代际和单个 Building/Validating 代际。`projection_pointer` 通过复合外键指向当前代际。Checkpoint 和投影行通过 Organization、Projection Name 和 Generation 隔离。测试 Harness 将 Generation 编入消费者身份，验证逻辑键 `consumerName + generation + eventId`。

每次投影事务先锁定并校验 Generation 状态和 Token，再执行 Receipt、Gap、投影行和 Checkpoint。切换事务锁定 Pointer 与目标 Generation，重新对比源快照、目标快照和已保存校验快照后更新两个 Generation 与 Pointer。

## 4. 实时双写、重放与重启

在线代际先消费两个分区事件，随后创建空的影子代际。新事件到达时，Router 先让在线代际成功提交，影子代际因缺少版本 `0` 拒绝版本 `1`。该投递保持可重试，在线代际的 Receipt 阻止重试产生重复副作用。

新 Harness 实例模拟进程重启，它只读取 PostgreSQL 中的 Generation、源事件、Receipt 和 Checkpoint，按分区顺序重放两次。最终影子代际为 3 行、3 个 Receipt 和 2 个分区 Checkpoint，规范快照与源快照一致。

## 5. 缺口与事务回滚

空分区首先收到 Aggregate Version `1` 时抛出 `ProjectionGapException`。事务后的 Receipt、投影行和 Checkpoint 数量全部为 0。补入 Version `0` 并按顺序重放后，两个版本收敛。

另一个样本在写入投影行后注入 Projector 异常。Receipt、投影行和 Checkpoint 全部回滚，使用相同 Lease 重试可以成功提交。

## 6. 构建失败与成员处置

样本在在线代际保存一条投影和成员 `READ` 处置，完成影子重放后将影子代际置为 `FAILED`。Pointer 仍指向原在线代际，影子代际无法切换，成员处置保持 `READ`。

该样本确定 Inbox 将来使用“Generation 来源投影 + 稳定成员处置”的合并查询，影子表只承载可重建来源。

## 7. 校验、切换、Cursor 与 Fencing

影子代际在源行数和规范 SHA-256 一致后进入 `VALIDATING`。切换事务再次计算当前快照，然后原子完成：

```text
old ACTIVE -> RETIRED
target VALIDATING -> ACTIVE
pointer old -> target
fencing token old/target + 1
```

旧 Cursor 携带旧 Generation，切换后抛出 `ProjectionCursorExpiredException`。切换前取得的旧 Generation Lease 因 Token 变更无法写入，新事件只进入新在线代际。

验证快照完成后再提交一个新事件时，首次切换因当前 Count/Hash 与保存快照不一致而拒绝。重新校验后切换成功。

## 10. 结论

M6-S01 验证通过。影子 Generation 可以在实时事件持续到达时从全量 DomainEvent 恢复，Generation Receipt 可以吸收实时与历史重复，版本缺口和 Projector 异常可以完整回滚。规范校验、原子 Pointer 和 Fencing Token 形成安全切换边界，在线代际和 Inbox 成员处置在失败重建中保持不变。
