# M7-S03 密码与登录防护验证记录

> 任务：`M7-S03`<br>
> 日期：2026-08-28<br>
> 结论：通过<br>
> 长期决策：[ADR-025](../adr/ADR-025-本地密码与登录防护参数.md)（PROPOSED）

## 1. 验证目标

M7-S03 以 Spring Security 7.0.5 的真实 PasswordEncoder 验证：

1. Argon2id 与 BCrypt 候选参数在 2C2G、8C16G Linux Profile 的延迟、吞吐和近似堆峰值；
2. 适合 CrewScope 共享 Agent/Task 工作负载的哈希并发上限和有界拒绝；
3. code point 与 UTF-8 byte 双重密码输入预算；
4. 登录标识/网络限流、失败窗口、临时锁定和恢复；
5. 已知账号、未知账号和锁定账号的公开失败与 Hash 工作量一致性；
6. BCrypt/较弱 Argon2id Credential 的成功登录后渐进 Rehash 边界。

本 Spike只增加测试范围的 Bouncy Castle、可执行测量夹具和长期决策，不替换现有 Bootstrap PasswordEncoder。正式 Credential、Redis 限流和 WebFlux 装配归属 M7-D03、M7-I03 与 M7-I04。

## 2. 候选矩阵与方法

真实编码器候选：

| 候选 | 参数 |
|---|---|
| Argon2id M19/T2/P1 | memory 19,456 KiB、iterations 2、parallelism 1、salt 16 byte、hash 32 byte |
| Argon2id M32/T2/P1 | memory 32,768 KiB、iterations 2、parallelism 1、salt 16 byte、hash 32 byte |
| Argon2id M32/T3/P1 | memory 32,768 KiB、iterations 3、parallelism 1、salt 16 byte、hash 32 byte |
| BCrypt 10/11/12 | Spring BCryptPasswordEncoder strength 10、11、12 |

每个候选先执行 2 次预热，再对每个并发级别执行 `max(7, concurrency × 2)` 次编码。P50/P95 使用 nearest-rank；吞吐按整个并发批次 Wall Time 计算；堆峰值增量来自 JVM MemoryPool Peak Usage，是包含编码器临时对象和 JVM 分配行为的安全侧近似值，不等同于 Argon2 的 memory 参数或进程 RSS。该 Runner 用于同版本相对校准，不替代 JMH 微基准。

可重复入口：

```bash
M7_S03_WARMUP=2 M7_S03_SAMPLES=7 \
  ./scripts/m7-s03-password-profile.sh <profile-name> 1,2,4,8
```

Runner 输出 Profile、可用处理器、最大堆、Java、OS/架构和 CSV。CI 只运行确定性策略测试，不用共享 Runner 的耗时结果自动修改安全参数。

## 5. 选定 Argon2id 并发结果

| Profile | 并发 | 操作数 | P50 ms | P95 ms | 最大 ms | 吞吐 ops/s | 近似堆峰值增量 MiB |
|---|---:|---:|---:|---:|---:|---:|---:|
| 2C2G | 1 | 7 | 122.13 | 133.71 | 133.71 | 8.44 | 139.0 |
| 2C2G | **2** | 7 | **143.09** | **168.07** | **168.07** | **12.19** | **219.0** |
| 2C2G | 4 | 8 | 333.38 | 439.86 | 439.86 | 10.40 | 326.5 |
| 8C16G | 1 | 7 | 133.29 | 191.42 | 191.42 | 6.59 | 118.7 |
| 8C16G | 2 | 7 | 147.19 | 178.07 | 178.07 | 12.65 | 162.0 |
| 8C16G | **4** | 8 | **204.00** | **225.53** | **225.53** | **19.11** | **335.9** |
| 8C16G | 8 | 16 | 225.62 | 285.78 | 285.78 | 31.58 | 783.9 |

2C2G 从 2 路增加到 4 路后吞吐下降且 P95 增至 439.86 ms，因此 Permit 固定为 2。8C16G 的 8 路吞吐更高，但近似堆峰值从四路的 335.9 MiB 增至 783.9 MiB；CrewScope 还要同时运行 Agent、Task、PostgreSQL 和 Redis，选择 4 路作为稳定默认值。

## 6. 登录防护冻结结果

```text
password registration budget = 12..128 code points AND <= 512 UTF-8 bytes
password authentication budget = <= 128 code points AND <= 512 UTF-8 bytes
identifier bucket = 10 attempts / 15 minutes
controlled network bucket = 60 attempts / 5 minutes
account temporary lock = 10 failures / 15 minutes -> lock 15 minutes
hash permit = 2 on 2C2G, 4 on 8C16G
permit wait = 100 ms
permit overflow = 429 too_many_requests + Retry-After: 1
credential failure = 401 invalid_credentials
```

确定性 Fixture 的拒绝行为：两个 Permit 被阻塞后，第三个请求在 100 ms 预算内返回拒绝，`started=2`、`rejected=1`，没有启动第三次昂贵工作。标识第 11 次和网络第 61 次尝试返回 lookup-independent 的 `too_many_requests`，窗口到期后恢复。已知账号第 10 次失败进入 15 分钟锁定；锁定期间与未知账号都执行一次 Dummy/真实 Hash 工作并返回相同 `invalid_credentials`，锁定到期后成功登录清空账号失败窗口。
