# M7：开放用户体系与登录体验执行清单

> 对应总计划：[CrewScope 实施计划](../CrewScope-实施计划.md) M7<br>
> 前置条件：M6-Q04 MVP Release Gate 通过，Principal、TeamMember、TeamRole、Redis、审计、部署与双入口前端基线稳定<br>
> 目标周期：3–4 周，按“认证内核 → 账号与会话 → Onboarding/邀请 → 前端闭环 → 安全门禁”纵向推进<br>
> 目标结果：用户通过 CrewScope 自有登录与注册页面进入平台，拥有独立账号和服务端会话，可创建第一个 Team、获得默认 Personal Agent、邀请其他用户并以各自身份协作；浏览器不再出现 HTTP Basic 原生认证弹窗<br>
> 当前进度：`M7-S01` 至 `M7-S04`、`M7-D01` 至 `M7-D08` 已完成，下一任务为 `M7-I01`

## 1. 出口结果与范围

M7 完成后具备：

- CrewScope 本地 `UserAccount`、可扩展 `LoginIdentity`、`LocalCredential` 与 Organization Binding；
- `OPEN / INVITE_ONLY / DISABLED` 三种注册模式及部署级安全默认值；
- 基于 Spring Security、Spring Session Data Redis 和服务端 Cookie 的登录会话；
- 正式 `/login`、`/register`、`/onboarding`、`/account` 与 `/invite#token=...` 页面；
- 注册、登录、退出、当前会话、资料修改、密码修改、首次 Team 创建和邀请接受 API；
- 新账号创建第一个 Team 后自动成为 Owner，并复用 M1 事务创建默认 Workspace、内置角色和 Personal Agent；
- Team Owner/Admin 创建、查看和撤销一次性邀请链接，已登录或新注册用户均可接受；
- Bootstrap Operator 迁移到相同登录页，人类登录凭证与 Prometheus 监控抓取凭证分离，浏览器业务入口不再启用 HTTP Basic Challenge；
- 密码哈希、登录限流、临时锁定、Session 固定防护、CSRF、Cookie 和账号枚举防护；
- 两个真实独立用户完成“注册—建 Team—邀请—加入—协作—退出—重新登录”的纵向 E2E。

M7 的 `OPEN` 注册面向单 Organization 自托管实例，不宣称公共多租户 SaaS 隔离。M7 不包含企业 OIDC/LDAP/SCIM 接入、飞书/GitHub 社交登录、邮件发送、邮箱验证、忘记密码邮件、MFA、Passkey、跨部署统一账号、跨 Organization 切换、平台级计费、账号合并、管理员冒充登录或公开 SaaS 反滥用运营系统。`LoginIdentity` 和 Account/Principal 分层为这些能力保留扩展边界，但不提前实现外部身份流程。

## 2. 产品闭环

```text
访问 CrewScope
  -> Session Store 查询当前账号
  -> 未登录进入 /login
  -> 用户登录，或在 OPEN 模式进入 /register
  -> 服务端验证 Credential 并旋转 Session ID
  -> 当前账号没有 ACTIVE Team 时进入 /onboarding
  -> 创建第一个 Team
  -> 原子创建 Owner Membership、默认 Workspace、内置 Role Grant 与 Personal Agent
  -> 进入 Conversation / Control 双入口
  -> Owner 创建一次性邀请链接
  -> 第二个用户登录或注册并接受邀请
  -> 第二个用户获得 MEMBER Grant 与默认 Personal Agent
  -> 两个用户以不同 Principal 协作，权限与 Audit 可区分
  -> 退出登录使服务端 Session 失效并返回 /login
```

## 3. 核心决策

### 3.1 Account、LoginIdentity 与 Principal 分层

- `UserAccount` 是平台登录主体，保存用户名、规范邮箱、展示名、状态、安全版本和 `USER / OPERATOR` 平台角色；自助注册始终为 `USER`；
- `LoginIdentity` 保存登录提供方与稳定 Subject。M7 只实现 `local`，Subject 使用不可变 Account ID，不使用可修改邮箱；
- `LocalCredential` 只保存强密码哈希、算法标识、密码版本和修改时间，不进入 DomainEvent、Audit、日志或查询 DTO；
- `AccountOrganizationBinding` 显式允许 Account 进入 Organization，并绑定该 Organization 内的 USER Principal；Binding 单向引用 Account 与 Principal，Principal 不反向依赖 Account，避免身份模型循环；
- `Principal` 继续作为 Organization 内用户、Agent 和 Service 的统一业务 Actor；TeamMember 与 TeamRole 不感知密码和 Session；
- 新本地 Account 创建的 USER Principal 不再把 `principal.identity_provider/external_subject` 作为登录真相；旧 Bootstrap/OIDC Principal 的 ExternalIdentity 作为兼容数据保留，登录映射的唯一权威来源是 LoginIdentity 与 Binding；
- M7 的本地部署默认绑定一个 Bootstrap Organization，同一实例中的 Account 只会话化一个 ACTIVE Binding。数据库仍使用 `Account + Organization` 约束，不把 Account 与单一 Organization 永久耦合；多 Organization 选择和企业 Issuer Binding 延后。

### 3.2 服务端 Session

- 浏览器认证使用服务端 Session，不向前端签发长期 JWT，不把 Token 保存到 `localStorage`；
- Spring Security Context 保存到 Spring Session Data Redis，Cookie 使用 `HttpOnly`、部署环境 `Secure`、`SameSite=Lax` 和受控 Path；
- 登录成功必须旋转 Session ID，退出必须使服务端 Session 失效并清理 Cookie；
- `GET /api/v1/auth/session` 对匿名请求返回 `authenticated=false`、Registration Mode 与 CSRF Header/Token 公开坐标，对已登录请求追加 Account、Principal、Organization、Team 摘要和权限；防 CSRF Token 是同源前端需要回传的公开值，只出现在受控 CSRF Cookie、Session 公开投影和写请求 Header，不进入 `localStorage`、`sessionStorage`、IndexedDB 或 Telemetry；
- 所有浏览器写请求都使用 Cookie CSRF Token 与同源校验；登录、注册和邀请接受同时使用独立的未认证限流与一次性校验边界；
- Redis 短暂不可用时认证失败关闭，不回退到客户端身份或无状态超级用户。

### 3.3 开放注册与 Onboarding

- `OPEN` 允许用户自助注册；`INVITE_ONLY` 只接受有效邀请上下文；`DISABLED` 关闭新本地账号；
- 注册请求只接受用户名、邮箱、展示名、密码和可选邀请 Token，不接受 Organization、Principal、Team、Role 或权限；
- 用户名与邮箱使用确定性规范化、显示值与规范值分离，冲突响应不泄漏其他账号细节；
- 密码策略以长度、常见密码拒绝和最大输入预算为主，不使用复杂字符拼凑规则；
- 无邀请注册创建 Account、Identity、Credential、Organization Binding 和 USER Principal，由用户显式完成 Onboarding 创建 Team；带邀请注册在同一事务锁定并消费邀请、创建 Membership，不先创建一个未绑定邀请的账号；
- Team 创建复用 M1 `TeamCreationService`，禁止 M7 再实现一套 Team/Role/Personal Agent 初始化逻辑。

### 3.4 Team Invitation

- 邀请保存 Team、邀请人、可选目标邮箱、目标内置角色、过期时间、状态和 Token Hash；
- 明文 Token 只在创建成功时返回一次，数据库、日志、Audit、前端 Store 和列表响应只保存安全摘要；
- 邀请链接把 Token 放入 URL Fragment，Fragment 不发送到 Web/Nginx；前端读取到进程内存后立即清除地址栏，再通过 POST Body 执行 Preview/Accept；
- Preview 只返回 Team 名称、邀请人展示名、过期状态和是否需要登录，不返回成员目录或内部 Scope；
- Accept 在同一事务锁定邀请，验证 ACTIVE Account、Organization Binding、Team 当前状态、邀请版本和 Token Hash，再复用成员加入服务；
- 同一 Account 重复接受收敛为既有 Membership；Token 重放、撤销、过期、目标邮箱不匹配和跨 Organization 使用失败关闭；
- M7 不发送邮件，Owner 复制邀请链接交付。后续邮件/飞书通知只消费相同 Invitation 事实。

### 3.5 Bootstrap、监控身份与企业扩展

- V30 升级时使用现有 `bootstrap/crewscope-monitor` ExternalIdentity 精确查找 USER Principal；存在时创建 Account/Binding 并保留 Principal ID、TeamMember 和 Audit 历史，不存在时才创建新 Operator USER Principal；
- 旧 `bootstrap_password` 只作为人类 Bootstrap Operator 初始/轮换凭证输入，启动时不回显；Operator Account 持有 `OPERATOR` 平台角色，自助注册无法获得该角色；
- Prometheus 改用独立机器账号与 `monitoring_password` Secret，只能访问受控 Actuator 抓取路径，不创建 UserAccount、TeamMember 或业务 Session；升级 Guard 拒绝 Operator 与监控继续共用凭证；
- Web 业务入口不返回 `WWW-Authenticate: Basic`。Basic 仅可用于精确匹配的机器运维路径，其 SecurityWebFilterChain 与普通 Web/REST Session 链分离；
- 后续 OIDC 只新增 `LoginIdentity` 和认证 Adapter，将同一 Account 映射到现有 Principal，不改变 TeamMember、权限、Conversation 或 Task 授权模型。

## 11. 配置与 API 基线

### 11.1 关键配置

```yaml
crewscope:
  security:
    mode: local
    session:
      ttl: 12h
      maximum-sessions: 5
      cookie:
        secure: true
        same-site: Lax
  registration:
    mode: OPEN
  invitation:
    ttl: 7d

spring:
  session:
    # Spring Boot 4 使用 data.redis 前缀，M7-I02 以配置测试防止静默回退。
    data:
      redis:
        namespace: crewscope:session
```

生产或公网部署必须使用 HTTPS 并启用 Secure Cookie。开发环境可显式关闭 Secure，但配置 Guard 必须拒绝把该设置用于生产 Profile。密码哈希使用 M7-S03 实测确定的 Argon2id M32/T3/P1；2C2G/8C16G 分别使用 2/4 个有界 Hash Permit，完整参数和重测条件由 [ADR-025](../adr/ADR-025-本地密码与登录防护参数.md) 管理。

### 11.2 公开 API

```text
POST   /api/v1/auth/register
POST   /api/v1/auth/login
POST   /api/v1/auth/logout
GET    /api/v1/auth/session

GET    /api/v1/account
PATCH  /api/v1/account
POST   /api/v1/account/password
POST   /api/v1/account/sessions/revoke

GET    /api/v1/onboarding
POST   /api/v1/onboarding/team

POST   /api/v1/organizations/{organizationId}/teams/{teamId}/invitations
GET    /api/v1/organizations/{organizationId}/teams/{teamId}/invitations
POST   /api/v1/organizations/{organizationId}/teams/{teamId}/invitations/{invitationId}/revoke
POST   /api/v1/invitations/preview
POST   /api/v1/invitations/accept
```

登录和注册接受 JSON，请求体字段采用固定白名单。Session Cookie 不进入响应 DTO。邀请 Token 只允许出现在创建成功的一次性响应、邀请链接 Fragment、Preview/Accept POST Body 和页面进程内短期状态，不进入 HTTP Path/Query、查询列表、Telemetry、错误详情或持久浏览器存储。

## 12. M7 Release Gate

M7 完成需要同时满足：

1. 浏览器访问 Web 不再出现 HTTP Basic 原生认证弹窗；
2. OPEN、INVITE_ONLY 和 DISABLED 注册模式行为与配置一致；
3. 两个用户拥有独立 Account、Session、Principal、TeamMember、Personal Agent 与 Audit 身份；
4. 注册、登录、退出、Session 过期、密码修改和全部 Session 撤销闭环通过；
5. 首次 Team 创建只复用一条 M1 初始化事务，不产生重复 Workspace、Role Grant 或 Personal Agent；
6. 邀请 Token 明文不落库且只能成功接受一次；
7. 密码明文/哈希、Session ID、认证 Cookie 和邀请 Token 不进入日志、事件、Audit、Trace、指标或公开 DTO；防 CSRF Token 只出现在受控 CSRF Cookie、Session 公开投影和同源写请求 Header，不进入其他浏览器持久存储或 Telemetry；
8. Session 固定、CSRF、开放重定向、账号枚举、暴力尝试和跨 Organization/Team 攻击全部阻断；
9. Redis、API 进程和数据库故障不会产生半注册、重复 Membership 或已退出 Session 恢复；
10. Team Beta 从 V30 升级到 V32 后 Operator 可通过登录页进入，既有 M0–M6 数据和权限保持有效；
11. 登录、注册、Onboarding、账号和邀请页面通过双视口、键盘、Axe、视觉和离线/错误状态门禁；
12. 全量 Maven、Vitest、生产构建、Histoire、Playwright、镜像、迁移、备份恢复和文档检查通过。
