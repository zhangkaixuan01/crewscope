> 评审来源：[M8 后全面架构与产品体验 Review](../reviews/M8后-全面架构与产品体验Review.md)<br>
> 计划粒度：12 个 Feature 级工作包<br>
> **实现前必读：[§10 实施细则（方向边界，非执行细则）](#10-实施细则方向边界非执行细则)** ——只写不论 Spike 结论如何都成立的边界：RLS 不得成为唯一防线、单机形态不得退化、`organization_id` 回填是数据迁移、落点的「不要新建平行概念」清单，以及十项全部由 `M12-S01` 决定的开放项；本清单只冻结方向与边界，不做可领取级拆分

## 1. 目标

M8 让 CrewScope **可发行**，M9 让它**好用**，M10 让 Agent **懂团队**，M11 让团队**能同屏协作并对外开放**。M12 回答最后一个问题：**能不能卖，能不能托管，能不能规模化运行。**

当前 CrewScope 的全部设计假设是"单 Organization 自托管"。M7 引入了开放用户体系，但 Organization 始终只有一个；执行拓扑是单机 Docker Compose；没有企业身份、没有配额、没有 SLO、没有租户隔离。这些在自托管场景下不是问题，在托管交付与企业采购场景下是硬门槛。

M12 完成后，CrewScope 既可以继续作为单机自托管产品发行，也可以作为多租户托管服务运行，且两种形态共用同一套代码与同一套语义。

## 2. 出口结果

1. 多 Organization 成为一等边界，数据、执行、配额、审计在 Organization 层完全隔离；
2. 企业身份接入：OIDC/SAML SSO、SCIM 用户同步、MFA、会话策略；
3. 配额与计量：按 Organization 的执行、Token、存储、并发配额，可配置、可监控、可告警；
4. Kubernetes 执行拓扑：Worker 可在 K8s 上按需伸缩，与既有 Lease/Fencing/Checkpoint 语义兼容；
5. SLO 与容量治理：关键路径 SLI 定义、错误预算、容量模型与压测基线；
6. 数据治理：租户数据导出、删除、保留策略与合规证据；
7. 单机自托管形态保持完全可用，不因多租户改造而退化。

## 3. 范围与非目标

### 3.1 本期范围

- Organization 隔离采用**共享 Schema + 强制租户列 + 行级安全**方案，不做每租户独立数据库；
- SSO 作为可选身份源与既有本地账号共存，不强制迁移；
- K8s 执行拓扑作为可选部署形态，Docker Compose 形态继续作为默认发行目标；
- 配额是**软硬双层**：软配额告警，硬配额拒绝，两者均可按 Organization 配置；
- 全部改动保持既有领域语义、事件版本与恢复语义兼容。

### 3.2 非目标

- 计费与支付集成（配额与计量是前置，实际计费不在本期）；
- 跨 Organization 的知识或资源共享；
- 多区域部署与跨区域数据同步；
- 自动扩缩容的成本优化策略（先有拓扑与指标，再谈优化）；
- 合规认证本身（SOC2/ISO 的审计流程），M12 只交付技术侧证据能力。

## 4. 核心决策

### 4.1 租户隔离在数据层强制，不在应用层自觉

所有租户相关表新增非空 `organization_id`，并启用 PostgreSQL 行级安全（RLS），会话级设置租户上下文。应用层的遗漏不会导致跨租户泄漏——**数据库是最后一道防线，且必须是有效的防线**。

这是本里程碑最重要的一条决策：应用层过滤是性能优化，RLS 才是安全边界。

### 4.2 单机形态是一等公民，不是退化形态

多租户改造不得让单机自托管变复杂。单 Organization 部署下，租户上下文由启动时固定注入，用户不感知任何多租户概念。**任何"仅托管形态可用"的核心功能都视为设计失败。**

### 4.3 SSO 与本地账号共存

Organization 可配置身份源策略：仅本地、仅 SSO、二者共存。SSO 用户首次登录自动置备，角色由 SCIM 或 IdP 声明映射。既有 Session、权限与审计模型不变。

### 4.4 配额挂在 Organization，计量挂在事件

配额配置是 Organization 的权威事实；用量计量从既有事件流派生（沿用 ADR-026 原则），不建立第二套用量状态。硬配额在命令入口处裁决并返回稳定错误码，不在执行中途中断已开始的任务。

### 4.5 K8s 拓扑不改执行语义

Worker 在 K8s 上运行时，Lease/Fencing/Checkpoint/Outbox 语义完全不变——这些机制本就是为"Worker 可能随时消失"设计的，K8s 只是让这件事更频繁发生。Pod 被驱逐与 Worker 进程崩溃在语义上等价。

M8-I01 移除的 Kubernetes Client 依赖在本里程碑以**独立可选模块**形式重新引入，默认构建不包含。

### 4.6 SLO 先定义再优化

先定义 SLI（Conversation 首 Token 延迟、Task 排队时长、执行成功率、API P95、通知送达率）与目标值，建立错误预算与容量模型，再谈优化。没有基线的性能工作是猜测。

## 8. M12 Release Gate

1. 租户隔离在数据库层强制生效，绕过应用层的直连 SQL 仍无法跨租户读写；
2. 单 Organization 自托管形态零额外配置、零多租户概念暴露、功能与 M11 一致；
3. Organization 切换不泄漏任何上一租户的缓存、Store 或指标；
4. SSO/SCIM/MFA 可用，IdP 不可用时有明确降级，本地账号路径不受影响；
5. 软硬双层配额可配置、可裁决、不中断已开始的执行；
6. 用量与 SLI 均为派生事实，不复制权威状态，不跨租户泄漏；
7. K8s 形态下 Pod 驱逐与节点故障不破坏执行正确性，Sandbox 隔离等级不低于 Compose；
8. 默认构建不包含 Kubernetes Client；
9. 全部 SLI 可采集，错误预算可告警，容量结论有压测支撑；
10. 租户数据可导出、可删除，保留策略可配置且有合规证据；
11. 多租户固定攻击集与固定故障集全部通过；
12. 双形态（单机 Compose / K8s 多租户）均完成端到端验证；
13. M0–M11 全量固定攻击、故障、恢复、迁移与浏览器门禁零回归。

## 9. 任务规模约定

本清单为 Feature 级方向基线，**不作为可领取的执行清单使用**。进入 M12 前必须完成 `M12-S01`，并基于 Spike 结论把 `D01`、`I01`、`I02` 三个高风险工作包细化到可领取粒度。

若 `S01` 结论表明多租户改造的代价超过当期产品价值，允许把 M12 拆为两个里程碑：M12 只做企业身份、配额与 SLO（不做多租户隔离），多 Organization 后置到 M13。**这个判断必须基于 Spike 数据，而不是基于排期压力。**

## 10. 实施细则（方向边界，非执行细则）

> **本节刻意只写边界，不写实现。** §9 已声明本计划「不作为可领取的执行清单使用」，且 M12 是否按原样执行本身取决于 `M12-S01` 的结论（§9 允许拆为 M12 + M13）。在 Spike 之前把 RLS 策略、SSO 库选型、K8s 拓扑写进文档，只会制造「文档写了所以就这么做」的伪共识。
>
> 因此本节固化的是三类**不论 Spike 结论如何都成立**的东西：不许越的红线、不许被单一机制承担的安全边界、不许被牺牲的既有形态。其余全部标注「由 `S01` 决定」。

### 10.1 红线清单

| 红线 | 判定方式 |
|---|---|
| **RLS 不得成为唯一防线** | 应用层的 `ExecutionScope ∩ Ownership` 求交必须**继续存在且继续生效**。RLS 是纵深防御的第二层，不是替代品。`Q01` 的固定攻击集必须**同时**包含「绕过应用层直连数据库」与「应用层越权但 RLS 未启用」两类场景——只测一类等于只有一层 |
| 单机形态必须继续可用 | 自托管 Compose 单 Organization 部署的功能完整性与升级路径不得退化（§8 `Q02` 已定为双形态验收）。**任何「只有多租户模式才能用」的核心功能都是越界** |
| `organization_id` 回填是数据迁移 | 不是结构迁移。必须有独立的回填计划、进度可观测、可中断可续、可回滚，并在真实数据量上验证耗时。**不允许用一条 `UPDATE` 全表** |
| 既有权限模型不被 Organization 角色覆盖 | Organization 级角色（Owner/Admin/Member/Billing）与 Team 级角色是**两个正交维度**，求交而非替代；不得出现「Org Admin 因此自动拥有所有 Team 的写权限」这类隐式提权 |
| K8s 是独立可选模块 | 不引入对 K8s Client 的硬依赖；关闭时执行拓扑与 M11 完全一致（M3 曾移除过 K8s，重新引入不得重犯「核心路径依赖集群」的错误） |
| SSO / SCIM 不绕过既有 Session 与审计 | 联邦身份最终仍落到既有 Session 模型与 Audit；不新建第二套会话体系 |
| 已发布迁移不可变 | 含 M9 `V37`+、M10 `V39`–`V43`、M11 `V44`+ |
| M9–M11 的体验 DoD 不回退 | M12 新增页面从第一版满足 M9 §10.10 十条 DoD；菜单与路由清单继续同步（M11 结束为 21 项） |

### 10.2 迁移与编号边界

M12 的迁移编号从合并时实际最大值 +1 顺延。**不预先分配文件名**——`D01` 的表清单完全取决于 `S01` 选定的隔离方案（共享 Schema + RLS / Schema per tenant / 数据库 per tenant 三种代价差异巨大）。

只固化三条约束：

1. **隔离基座的迁移必须可分段执行**：加列（可空）→ 回填 → 加非空约束与外键 → 启用 RLS，**四步四个迁移文件**。合成一个文件意味着大表上的长事务与不可回滚；
2. **RLS 策略与应用层求交必须有对账测试**：同一组查询在「RLS 开 + 应用层开」「RLS 开 + 应用层绕过」「RLS 关 + 应用层开」三种配置下的结果集断言，证明两层各自独立有效；
3. **配额与计量表的写入必须与业务事务解耦**（沿用既有 Outbox 语义），否则计量失败会阻塞业务。

### 10.3 落点边界

只固化「不要新建平行概念」这一类判断，具体类名由 `S01` 后细化：

| 能力 | 落点 | 不要 |
|---|---|---|
| Organization 领域模型 | `domain/organization/`（新建） | 不要塞进 `domain/team/`——Organization 是 Team 的上级作用域，混包会让作用域链无法表达 |
| Organization 管理 | `application/organization/`（新建） | 不要叫 `tenant`——用户可见概念是 Organization，内部命名与用户语言一致可省掉一层翻译 |
| 配额与计量 | `application/quota/`（新建） | 不要放 `application/observability/`——观测是只读聚合，配额是有判定与拒绝的强制机制，两者的失败语义不同 |
| SLO 与容量 | `application/observability/`（**既有包，就地扩写**） | 不要新建 `application/slo` |
| 企业身份联邦 | `crewscope-integration`（外部身份源集成）+ `application/identity/`（既有包，会话与账号语义） | 不要新建第二套会话模型 |
| K8s 执行拓扑 | **独立 Maven 模块**（可选依赖，默认不启用） | 不要放进 `crewscope-infrastructure` 的必选依赖 |
| 前端 | 沿用 M9 §10.4 目录规则；`src/domains/{organization,quota}/`、`src/pages/{OrganizationSettingsPage,UsagePage,SessionsPage}.vue` | 不要为 Organization 切换器另起一套全局状态——复用 M9 的 `src/app/preference.ts` 与既有 scope store 的作用域切换范式 |

### 10.5 「不要这样做」清单

| # | 偏差写法 | 正确做法 |
|---|---|---|
| 1 | 上了 RLS 就删/放松应用层求交 | 两层必须并存，且有三配置对账测试（10.2 第 2 条） |
| 2 | `organization_id` 一条 `UPDATE` 回填 | 四步四文件，可中断可续可回滚，真实数据量验证耗时 |
| 3 | Org Admin 自动拥有全部 Team 写权限 | 两个角色维度求交，不得隐式提权 |
| 4 | 核心执行路径依赖 K8s | 独立可选模块，关闭时与 M11 行为一致 |
| 5 | 为 SSO 新建第二套会话模型 | 联邦身份落到既有 Session 与 Audit |
| 6 | 配额校验写在业务事务里同步落计量 | 计量走 Outbox 解耦；否则计量故障阻塞业务 |
| 7 | 内部命名用 `tenant`，界面叫 Organization | 内外一致用 Organization |
| 8 | 把配额放进 `application/observability/` | 新建 `application/quota/`；判定机制与只读观测不同源 |
| 9 | 多租户模式下才有的核心功能 | 单机单 Organization 形态功能完整性不得退化 |
| 10 | 在 Spike 前按本节写实现 | 本节只是边界；实现细节由 `S01` 给出后再补一节执行细则 |

### 10.6 由 `M12-S01` 决定的全部开放项

**以下每一项在 Spike 前都没有答案，文档里也不应该有答案：**

1. 隔离方案（共享 Schema + RLS / Schema per tenant / 库 per tenant）的性能、运维与迁移代价对比，以及最终选型；
2. 受影响表的完整清单与回填耗时的真实数据量实测；
3. RLS 对既有查询计划的影响与索引调整清单；
4. 单机形态的兼容策略（是否启用 RLS、单 Organization 的默认行为）；
5. OIDC / SAML / SCIM / MFA 的库选型与自实现边界；
6. 会话策略的具体取值（超时、并发会话上限、强制登出语义）；
7. 配额的资源维度与软硬阈值的具体语义（软阈值告警还是降级、硬阈值拒绝还是排队）；
8. K8s 执行拓扑的形态（Job/Pod 生命周期、镜像与网络隔离、与既有 Docker Socket Proxy 隔离模型的关系）；
9. SLI 定义、SLO 目标值与容量模型；
10. **M12 是否按本计划整体执行，还是按 §9 拆为 M12（身份 + 配额 + SLO）与 M13（多租户隔离）。这个判断必须基于 Spike 数据，而不是基于排期压力。**
