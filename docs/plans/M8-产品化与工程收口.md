# M8：产品化与工程收口执行清单

> 里程碑状态：进行中（`M8-S01`、`M8-A01` 已完成，下一任务：`M8-A02`）
> 前置里程碑：M7-Q04
> 计划粒度：9 个完整工作包；每个任务可以包含多个模块和内部检查项，不再为 Controller、Repository、页面或脚本单独编号

## 1. 目标

M8 将 M0–M7 已完成的 Team Beta 能力收口为更容易配置、更容易部署、更容易维护和更适合公开发行的产品版本。

成员完成注册和首个 Team 创建后，可以通过统一 Setup Center 看清当前 Team 距离“可执行个人任务”“可执行 Coding 任务”“可进行团队交付”还缺少哪些事实，并从同一入口完成必要配置。维护者可以通过明确的依赖、配置、质量和发布门禁持续演进项目；部署者可以直接消费官方不可变镜像，并获得真实可用的 Trace、告警和自动备份能力。

M8 不扩展新的外部业务场景，重点补齐既有 Coding 与 GitHub 交付链路的产品化缺口。Conversation、WorkItem、Coding、Review、GitHub Draft PR、飞书通知和 Team Observer 继续使用既有领域合同；GitHub 仓库导入只负责把已授权远程仓库安全落到现有 Managed Root，不改变 Coding、Review 或 Delivery 的领域语义。

### 1.1 首要产品化阻断项

以下三个出口是 M8 的 P0，必须优先完成并作为同一条产品化主线验收：

1. **Setup Center**：新用户创建 Team 后能够看到能力级就绪状态、缺失事实、责任人和下一步操作，不再依赖多个管理页面之间的人工猜测；
2. **GitHub 仓库导入闭环**：已验证的 GitHub Connection Catalog 仓库能够安全导入 Worker Managed Root，自动进入 WorkProject 的受管 Repository Catalog，并可继续创建 CodingTarget；
3. **Worker 执行隔离**：Coding Agent 产生的代码执行环境与宿主机 Docker 控制面隔离，形成可审计、可验证的 Sandbox 信任边界，不能把 Docker Socket 作为默认的无限管理权限。

这三个出口未完成时，M8 只视为进行中，不得宣称 CrewScope 已达到可持续生产发行状态。

## 2. 出口结果

M8 完成时形成以下结果：

1. Team Setup Readiness 成为服务端权威派生视图，统一表达模型、Agent、WorkProject、Repository、Runtime 和可选协作集成的状态；
2. Web 提供 Setup Center 和首页就绪摘要，新用户不需要在多个错误页之间猜测配置顺序；
3. 核心超大文件和运行时 Port 按稳定职责收口，替代运行时 `UnsupportedOperationException` 的隐式实现缺口；
4. Maven 依赖、Spring 配置元数据、环境变量示例和本地开发边界保持可自动验证的一致性；
5. Git Tag/Release 可以发布 Backend/Web 同 Revision 的 GHCR 镜像、Digest Manifest、SBOM、Provenance 和签名；
6. Team Beta 的 Trace 有真实去向，Prometheus 有可执行告警，备份有自动调度，TLS 和本地 Compose 完成安全收口；
7. Worker Sandbox 与宿主机控制面完成隔离方案和运行时验证，部署文档明确隔离等级与残余风险；
8. 前端 Coverage 覆盖核心业务代码，CI 按变更范围分层执行并保留完整 Release Gate；
9. M8 Release Gate 通过真实空环境 Setup、完整任务闭环、升级恢复和公开发行验证。

## 3. 范围与非目标

### 3.1 本期范围

- Team Setup Readiness 只读取现有权威事实，不复制模型、Agent、Provider 或 WorkProject 状态；
- 必需能力与可选能力分开表达。基础对话、普通 WorkItem、Coding/GitHub、飞书通知拥有不同就绪条件；
- Setup Center 只调用既有受权命令或进入既有管理页面，不提供绕过权限的一键配置后门；
- GitHub Repository Import 将已验证的 Connection Catalog 项导入 Worker Managed Root，并在导入成功后创建现有 `LOCAL_MANAGED` RepositoryBinding；导入过程不接受浏览器 Remote URL，不把远程仓库直接伪装成 Coding RepositoryBinding；
- 架构重构保持公开 API、数据库事实、事件版本、幂等和恢复语义兼容；
- 正式发行以单机 Team Beta、Linux amd64 和 GHCR 为首个支持边界；
- P0 产品化主线必须包含 Setup Center、GitHub 仓库导入闭环和 Worker 执行隔离；
- 质量门禁同时覆盖 Java、Vue、配置、容器、文档和发行产物。

### 3.2 非目标

- Kubernetes 高可用执行拓扑；
- 多 Organization SaaS 控制面；
- OIDC/SAML 企业身份、MFA 和 SCIM；
- Vault/KMS 高可用凭证服务；
- Plugin 市场、任意第三方代码动态装载和 Provider 商店；
- PR 自动合并、生产发布和 Autopilot；
- Desktop 与 Mobile 客户端。

## 4. 核心决策

### 4.1 Readiness 是派生事实

Setup Readiness 不建立第二套业务状态。Application Query 在当前 Organization、Team、Member 和权限范围内读取现有 ModelConnection、AgentTemplate、AgentConfiguration、WorkProject、RepositoryBinding、Provider Connection 与 Runtime Health，生成带版本的公开快照。

单项状态使用闭合集合：

```text
READY | ACTION_REQUIRED | BLOCKED | UNAVAILABLE
```

每项同时标识 `required`、安全原因码、当前成员是否有处理权限和受信任的站内 `actionKey`。响应不返回 Credential、Endpoint、Provider 原始错误、内部数据库坐标或任意跳转 URL。

### 4.2 按能力判断就绪

Setup Center 不使用一个虚构的总百分比。它分别回答：

- 是否可以开始 Personal Conversation；
- 是否可以创建和执行普通团队任务；
- 是否可以执行 Coding/Review；
- 是否可以创建 GitHub Draft PR；
- 是否可以使用飞书通知和 Team Observer。

可选集成缺失不能阻断基础对话。没有 GitHub 时仍可执行非代码任务；没有飞书时仍可使用站内 Inbox 和 Activity。

### 4.3 重构保持行为兼容

大文件按稳定职责拆分，先建立 Characterization/Contract Test，再移动实现。M8 不借重构修改领域语义、数据库历史迁移、事件 Schema、权限策略或公开错误合同。

### 4.4 PR Gate 与 Release Gate 分层

Pull Request 优先提供快速反馈；Main 保留完整回归；Release 额外验证不可变镜像、签名、安装、备份恢复和真实浏览器闭环。路径过滤不能跳过与变更有关的门禁，Release Gate 继续要求所有必需证据存在且成功。

## 8. M8 Release Gate

M8 完成需要同时满足：

1. 新注册用户创建首个 Team 后可以从 Setup Center 看清必需项、可选项、处理权限和下一步；
2. 基础对话不被 GitHub/飞书等可选集成阻断，Coding、Review 和 Draft PR 只在各自权威前置条件满足时进入 READY；
3. TEAM GitHub Connection 管理员可以从已授权 Catalog 导入仓库，导入成功后该仓库出现在 Managed Catalog 并可创建 RepositoryBinding/CodingTarget；导入任务支持失败恢复且不暴露 Secret、Remote URL 或宿主路径；
4. Worker 与 Coding Sandbox 不直接获得宿主机 Docker 控制面，隔离方案经过逃逸攻击和权限边界验证；
5. Readiness 不复制领域状态，不暴露 Secret、Credential、Endpoint、Provider 原始错误或任意 URL；
6. 核心职责重构不改变现有 API、事件、数据库、幂等、权限和恢复语义；
7. 默认构建不携带未使用 Kubernetes Client，直接依赖和配置元数据通过自动化门禁；
8. 前端核心业务代码进入 Coverage 分母，Lint、格式、架构和依赖门禁低噪音且可持续执行；
9. PR、Main 和 Release 三层 CI 反馈范围明确，取消旧运行且不会因路径过滤漏掉相关验证；
10. 官方 Tag 发布 Backend/Web 同 Revision 的已扫描、可验证、固定 Digest 镜像和发行证据；
11. Trace 可查询或被明确关闭，关键故障产生可达告警，备份自动运行且空目标恢复成功；
12. 本地 Compose、TLS 模板、公开发行和开源协作文档完成安全与可用性收口；
13. 真实 Linux amd64 环境从正式发行产物完成空环境 Setup、双用户协作和完整研发任务闭环；
14. M0–M7 全量固定攻击、故障、恢复、浏览器和迁移门禁零回归。

## 9. 任务规模约定

M8 的编号代表可以独立验收的工作包，不代表一次提交。每个工作包允许包含若干内部 Checklist、多个小提交和必要的测试/文档更新；内部 Checklist 不再继续生成新的 M8 编号。只有当任务出现独立的产品出口、不同责任人或无法共同回滚的风险边界时，才新增任务编号。
